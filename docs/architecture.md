# Architecture (foundation, scene runtime and device-side interfaces, agent, voice and shell)

The highest authorities are `docs/superpowers/specs/2026-11-01-foundation-design.md` (foundation), `docs/superpowers/specs/2026-11-04-scene-runtime-core-design.md` (scene runtime), `docs/superpowers/specs/2026-11-05-scene-device-design.md` (scene device-side interfaces: background scenes, power levels, notifications, sensors, scene files), `docs/superpowers/specs/2026-11-05-agent-core-design.md` (agent core) and `docs/superpowers/specs/2026-11-06-mvp-design.md` (MVP: voice pipeline, memory and reminders, system shell and the wisp home screen). This document is an overview of the current code. Where it conflicts with a spec, the spec wins, but this document records only what has actually landed.

## Layering

```
┌──────────────────────────────────────────────────────────────────────┐
│  Entry   firmware/main (device) | simulator/ (PC)                    │
├──────────────────────────────────────────────────────────────────────┤
│  wisp_app    boot · system duties · diagnostics · PowerManager       │  ← portable
│  wisp_shell  shell: home and navigation · conversation · talk key    │  ← portable
│  wisp_agent  agent: conversation log · tools · loop · context        │  ← portable
│  wisp_scene  Lua scene runtime (third_party/lua)                     │  ← portable
│  wisp_ui     LVGL driver glue, UI task                               │  ← portable
├──────────────────────────────────────────────────────────────────────┤
│  wisp_admin  admin console routes · request filter · WebSocket       │  ← portable
│  wisp_voice  voice: capture · ASR/TTS · <say> parsing · playback     │  ← portable
│  wisp_net    HTTP types · WispPack · Wi-Fi · pairing                 │  ← portable
│  wisp_core   log · event bus · device registry · settings · storage  │  ← portable
├──────────────────────────────────────────────────────────────────────┤
│  wisp_hal    peripheral interfaces + capabilities (interfaces only)  │  ← portable
│  wisp_base   Result/ErrorCode · Value/Properties · JSON              │  ← portable
│  wisp_os     tasks/queues/locks/timers/clock/memory (interfaces)     │  ← portable
├──────────────────────────────────┬───────────────────────────────────┤
│  wisp_port_esp                   │  wisp_port_sim                    │
│  FreeRTOS + IDF drivers          │  std::thread + SDL2               │
│  + boards/<board>                │  + simulated peripherals          │
└──────────────────────────────────┴───────────────────────────────────┘
```

`wisp_base` and `wisp_app` are additions relative to the spec (see item 1 of "Refinements relative to the spec" below). The spec text places `Result`/`Value` under `wisp_hal` and boot orchestration in `wisp_ui`; the implementation splits them into two separate components.

## Dependency rules

1. The portable components (`wisp_base`, `wisp_os`, `wisp_hal`, `wisp_core`, `wisp_net`, `wisp_voice`, `wisp_admin`, `wisp_ui`, `wisp_scene`, `wisp_agent`, `wisp_shell`, `wisp_app`) must not include any platform header: `esp_*`, `freertos/*`, `driver/*`, IDF's `hal/*`, `soc/*`, `rom/*`, `lwip/*`, `mbedtls/*`, `SDL*`, `curl/*`, plus `sdkconfig.h`, `nvs.h`, `nvs_flash.h`, `sdmmc_cmd.h` and bmgr's generated `dev_*`/`gen_board_*` (file-name prefixes, without a directory). They may depend only on the C++20 standard library (including the POSIX file APIs such as `<unistd.h>`/`<sys/stat.h>`/`<dirent.h>`, which both ESP-IDF's VFS and the host provide, and which `StorageManager` relies on to walk, delete and rename files), LVGL, ArduinoJson, and other portable components, top-down by layer. Only `wisp_scene` may include the Lua headers (`lua.h`, `lauxlib.h`, `lualib.h`, `lua.hpp`, `luaconf.h`).
2. Each portable component may include only headers from its own layer or a lower one (in the order of the "Layering" section of this file: `wisp_base < wisp_os < wisp_hal < wisp_core < wisp_net < wisp_voice < wisp_admin < wisp_ui < wisp_scene < wisp_agent < wisp_shell < wisp_app`); depending on a "higher" layer is forbidden.
3. Only `wisp_port_esp`, `wisp_port_sim`, `boards/*`, `drivers/*` and the entry layer (`firmware/main`, `simulator/`) may touch the platform.
4. In the `wisp_component()` call of each `components/wisp_{base..app}/CMakeLists.txt`, `IDF_REQUIRES`/`HOST_LIBS` may name only two external dependencies, ArduinoJson (`wisp_base`) and LVGL (`wisp_ui`). This stops anyone from getting around the `#include` check by attaching a platform- or host-specific dependency to a portable component directly in CMake. `REQUIRES` may list only lower portable components; the only exception is components brought in unmodified under `third_party/`: `wisp_scene` may `REQUIRES lua`, and no other layer may.
5. `tools/check_layering.py` enforces these rules (`bash tools/ci.sh` runs it, after running the self-test `tools/check_layering_test.py`). It scans the `.hpp/.cpp/.h/.c` files under each portable component (except the ported font data under `wisp_ui/fonts/`) and its `CMakeLists.txt`.

## Boot flow

The device (`firmware/main/main.cpp`) and the simulator (`simulator/main.cpp`) share the same `wisp::app::App::start()` (`components/wisp_app/src/app.cpp`). They differ only in the `Platform` each provides (log sink, settings backend, `emit_line`, `request_power_off`, `heap_info`, `set_light_sleep` (scene device spec 4.1, switches automatic light sleep on and off in deep standby; may be empty), plus, added by sub-project 2, `random`, `http_server`, `http_client`, `assets`, `http_port` (default 8900), `captive_server`, `http_always_on`, `reboot`, `read_line`, `firmware` (the firmware upload writer `core::FirmwareUpdater`, connectivity spec 6.5; empty means web upload is not supported) and `firmware_version`, and, added by sub-project 3a, `install_image_decoders` (installs the platform's own LVGL image decoders on the UI task through `ui::UiConfig`; currently the baseline JPEG for `ui.image`: esp_new_jpeg on the device, LVGL's bundled TJpgDec in the simulator; PNG is handled by LodePNG, turned on in `lv_conf.h`, the same on both), `scenes_dir` (non-empty means development mode: scene code is read from this directory, read-only) and `scenes_data_dir` (the scene data root in development mode; when empty, `<internal root>/scenes` is used)):

1. **Log initialisation**: `wisp::log::init()` sets up a 32 KB in-memory ring buffer (in PSRAM on the device, ordinary memory in the simulator). Each record is a 16-byte header (`ts`, `seq`, length, level) plus the tag and message, evicted a whole record at a time. Reads copy only the raw bytes inside the lock and decode outside it. Calling `init()` again with the same size and memory type keeps the existing records. `seq` and `ts` are assigned under the same lock, and the `LogRecord` a sink receives is exactly the one in the buffer (connectivity spec 6.2).
2. **Board initialisation**: calls `Platform::board->init()` (`boards/<board>/board.cpp` on the device, `wisp::port::sim::SimBoard` in the simulator), which constructs the devices and registers them in `DeviceRegistry`. `init()` itself records only non-`Ok` `DeviceReport`s (missing/failed); `App::start()` then adds an `Ok` for every device in the registry that has not been reported.
3. **Core services**: starts the `EventBus`; calls `StorageManager::init()` (if mounting fails, sets the boot report's `storage` note to `"readonly"` and carries on degraded rather than aborting); starts the `ButtonService` and the storage thread `wisp.fs` (and, when the board registers a card (a `Storage` device with role `removable`), the SD I/O thread `wisp.sd.io`); starts a timer with a 2000 ms period (each time it hands `StorageManager::refresh()` through `core::StorageRouter` as a card job, `Medium::Sd`: to `wisp.sd.io`, or to `wisp.fs` without one, skipping when the previous one has not finished); and loads the model profiles on the storage thread (`core::ModelProfileService::init()`, which reads `secrets/models.json` in the System area; when only the old `secrets/llm.json` exists, it migrates it into one chat profile).
   **Scene storage** (scene spec 2.1/3, `components/wisp_app/src/scene_wiring.{hpp,cpp}`): starts `core::StorageWorker` (task `wisp.fs`), then, when the board registers a card (a `Storage` device with role `removable`), the SD I/O worker (task `wisp.sd.io`, `StorageWorker::sd_io_config()`) and the `core::StorageRouter` over both (`App::storage_router()`; if `wisp.sd.io` cannot start, or `kSdOwnWorker` in `scene_wiring.hpp` (the default of `SceneWiringDeps::sd_own_worker`) is false, card work stays on `wisp.fs` and boot carries on), constructs `core::SceneRepository` on `<internal root>/scenes` (for development mode see `scenes_dir` above), and runs `recover()` (which cleans up interrupted installs) to completion on `wisp.fs` before continuing, so that every later operation that lists or opens scenes sees the recovered state. It also constructs `core::SceneFiles` (`wisp.files`, scene device spec 7) on `<internal root>/scenes` (in development mode too, because `StorageManager` renames and deletes only inside the storage mount points); the same `wisp.fs` job runs its `scan()` after `recover()` (counting each scene's usage, and cleaning up and completing interrupted downloads). Its file calls are routed per scene (`SceneFiles::submit()`): a scene whose files are on the card runs them on `wisp.sd.io`, any other on `wisp.fs`. It follows `StorageManager::sd_cell()` on `wisp.bus` and, for each change of the card it sees (the cell's `changes` counter moved; the value at subscription is not one), recounts the scenes on the SD card: `sd_changed_begin()` on `wisp.fs` marks the card's scenes, each is recounted (`recount()`) on `wisp.sd.io`, and `sd_changed_end()` logs the card's files without a scene on `wisp.fs`. Changes that come close together may arrive as one, which one recount covers, since it reads what is there. `SceneWiring::stop()` drains both workers, stops `wisp.sd.io`, then `wisp.fs`. Without internal storage there are no scenes, and the system carries on degraded.
   **Notifications** (scene device spec 5, `core::NotificationService`): next the notification service is constructed and `load()`s `notifications.json` from the System area on `wisp.fs` (waiting at most 2 s; without a storage worker it reads on the boot thread). App's scene lifecycle inbox (`scene_lifecycle`, see "State cells and edge inboxes" below) removes all of a deleted scene's notifications. Once `PowerMonitor` is started, App follows its supply cell (`PowerMonitor::supply()`, on `wisp.bus`): when `charging` turns true it removes `battery_low`, and then, when `low` turns true, it first removes the old `battery_low` notification and posts one whose parameter is the battery percentage. Each edge is taken against the value last seen (`low` starts false, so a battery already low at subscription still posts), so a coalesced update acts once; the charging edge goes first, so a first sample that is both charging and low keeps the notice. A `battery_low` notice persisted from the last run is therefore dismissed when the device boots charging (the first sample is the charging edge), and a USB-only change while already charging does not dismiss it. The subscription is released with the notifications in `App::stop()`, before `PowerMonitor` is destroyed. When there are unsaved changes it starts an `os::Timer` with a 300 ms period (`wisp.notify`, created the first time it is needed and reused after that); each period does one whole `write_atomic` on `wisp.fs`, and the timer stops itself in its own callback once the disk is up to date. A failed post or write is retried with a delay starting at 600 ms and doubling; after 5 consecutive failures it stops and waits for the next change or a `flush()` to try again. Without a storage worker nothing is saved. `App::stop()` calls `close()` (stopping the timer) and then `flush(1000)` before the storage worker stops. Step 4 constructs `core::SensorService` before constructing `PowerManager` (shared subscriptions on the IMU with role `main`, task `wisp.imu`, no task without an IMU; once `PowerManager` is built, the service follows its level cell (`SensorService::follow_power(PowerManager::level_cell())`, on `wisp.bus`) and pauses all subscriptions at `Standby`/`DeepStandby` through `set_standby()`; on a wake with nothing subscribed it powers the IMU back down, which `PowerManager` woke through its caps, and when the cell's revision shows that a standby began and ended between two deliveries it does the same through `note_woken()`, so Active and Dim deliveries one at a time make no driver call; each subscriber is registered as shared under `imu.main` in `core::OccupancyRegistry`), and hands it to the scene runtime (`wisp.sensor`) and to hardware diagnostics (the self-check screen, opened on demand; it reads the IMU through the service with holder `system.selfcheck`; it unsubscribes while a scene covers it in the foreground and subscribes again on returning to the self-check screen, so the IMU is off while the foreground scene does not use it, and there is no such subscription while diagnostics is not open). It then starts `core::TonePlayer` (task `wisp.tone`; without an audio output with role `main` there is no task and alert tones are silently skipped); `PowerManager`'s activity callback (every touch reading and button edge, on the UI thread; on `wisp.bus` without a screen) calls its `silence()`. After the scene runtime is constructed, `app::NotificationRouter` is created as the listener of the notification service: for `wake` or `sound = "alarm"` with the screen off, it posts `exit_standby()` to the UI thread (an alarm must ring until the user touches, so it always turns the screen on); with a sound, it plays at `audio/notify_vol` as the settings cell holds it (no sound when the screen is off and it does not wake, since audio follows the screen, so a `tone` without `wake` is dropped while the screen is off); when a banner is installed, it shows the banner (installed by the status shell below). Tapping a notification removes it with `tap`, silences it, and through `SceneRuntime::deliver_notification()` brings the scene back to the foreground or launches it with `"notification"`, then calls `scene.on_notification(id)`.
4. **UI, system duties and the home screen**: if a `Display` with role `main` is registered (`display.main` in the simulator), applies the settings cell's `brightness` to it (the default when the stored value is missing or invalid; `PowerManager` follows the cell from there, on the UI thread), and starts `UiRuntime` on it (and on the touch panel with role `main`, if present). `Platform::font_image` (on the device the `fonts` partition that `app_main` maps, in the simulator `fonts.bin` read into memory) is passed in through `ui::UiConfig::font_image`; `UiRuntime::start()` validates it internally with `ui::open_font_image()` (vector font spec 3.6), and a failure only degrades text at 20 px and above to the bitmap font, without affecting the start of this step itself. Likewise, `Platform::glyph_image` (on the device the `glyphs` partition that `app_main` maps, in the simulator `glyphs.bin` read into memory, replaceable or disabled with `--glyph-image`) is passed in through `ui::UiConfig::glyph_image`, and `UiRuntime::start()` validates it with `ui::open_glyph_image()` (glyph partition spec 4.1); on failure, 16 px body text degrades along the fallback chain of glyph partition spec 4.3, again without affecting the start of this step itself. Otherwise it records `"mode": "headless"` in the boot report. In either case it looks up the `Power` device with role `main`, constructs `core::PowerMonitor` and `start()`s its own sampling timer (spec 6.3/6.7; publishes `power.charging.changed`/`power.battery.low` from the table below; completely inert without it), then constructs `PowerManager` (spec 6.7 and scene device spec 4; it holds a non-owning pointer to `PowerMonitor` and follows `App`'s own `core::WakeLockRegistry`) and starts its periodic idle-check timer `wisp.power` (one `tick()` per second, which also posts any `network`/`cpu` wake lock held for a full 30 minutes as the system notification `wakelock_long`; `screen` locks get no reminder, because one exists only while a scene is in the foreground, where the user can already see it). `PowerManager` manages five levels: `active`; `dim`, 10 seconds before the screen turns off (brightness drops to 30% of the set value, without calling the device); `standby` (pauses the UI and calls `set_power()` on each device according to its caps `standby`, going down in `DeviceRegistry::all()` order with audio input before output, and going up in exactly the reverse order; `Busy` is logged and retried on every later `tick()`); `deep_standby` (`standby` for a full `power/deep_after_s` with no `network` lock); and `Platform::set_light_sleep(true)`, called in `deep_standby` when built with `WISP_ENABLE_LIGHT_SLEEP=ON` and there is no `cpu` lock. A `screen` lock stops the idle timer. When wake locks change, it re-evaluates without waiting for the next `tick()`: with a UI, it always merges this into one job posted to the UI thread (even when the lock changes on the UI thread), and never switches levels on the thread that changed the lock. The `power` timeouts (`screen_off_s`, `deep_after_s`) come only from `SystemSettings::cell()` (applied from its value at construction, then by a subscription on `wisp.bus`); `tick()` reads no settings store, and a batch whose rollback failed reseeds the cell from storage, so the cell is brought back to what is stored before `set()` returns; out-of-range stored values are treated as the default (consistent with `SystemSettings::get()`). With a UI, every level switch runs on the UI thread. If `UiRuntime` was started, it then starts, in order on the UI thread, `app::SystemDuties` (`components/wisp_app/src/system_duties.{hpp,cpp}`: power key, Wi-Fi setup and pairing cards, factory reset and firmware confirmation dialogs, `WISP_PERF`, always resident whatever screen is in front) and `shell::Shell` (`wisp/shell/shell.hpp`, mvp spec 6.6: boots into the home screen, black background with the wisp centred in the safe area; during a turn it shows what the user said, the `<say>` text and the body text; four-way swipes move in and out of sub-pages; tapping an `agent_done` notification returns to the home screen; before navigating, a foreground scene is first sent away as by "Back"), and blocks until both have really run once. The self-check screen (`self_check_screen.cpp`, spec section 8) is now "Hardware diagnostics": it is not built at boot. `Shell::open_diagnostics()` has App build and load it on a new screen (serial command `diag`; the Settings page's "System → Hardware diagnostics" row), and a right swipe from the left edge returns to the home screen and tears it down. Scenes opened from it return to it when closed, and the shell sets the back gesture again when its screen is reloaded.
   **Scene runtime** (scene spec 3/6): with a `UiRuntime` and a repository, after `SystemLayer` and before the network, it constructs the scene HTTP proxy `net::SceneHttp` (when there is a `Platform::http_client`; it outlives the runtime and is stopped only at shutdown) and `scene::SceneRuntime` (not started yet), so that the admin console routes can get them (`scenes`, `scene_host` and `request_scene_delete` in `AdminDeps`). `device_status` (`wisp.device.info()`) runs on the scene task and does not touch flash: the battery comes from `PowerMonitor::last_status()`, and the Wi-Fi status comes from `NetWiring::wifi_state()` (which reads `WifiService::wifi_cell()`, whose lock is held only for memory work) and `network_expected()` (an atomic the `wisp.net` task writes on every loop: `WifiService::connection_expected()`, which the voice reads as `network_expected`); the lock of `WifiService::status()` may be held while flash is written, so it is not called on the scene task. The proxy and the runtime are started only after the home screen has been built (the screen a scene view replaces, and returns to when closed, is whatever is in front at the time, which at boot is the home screen), and it follows `PowerManager::level_cell()` on `wisp.bus` (also read once at start, so the first frame is right): `set_visible(false)` at `standby` and below, restored on wake (each delivery carries the cell's latest level, so a late one never leaves the scene hidden on a lit screen; a standby and wake that come together arrive as one delivery and the scene sees neither; `set_visible()` records the desired state and the message only wakes the scene task, so when the scene queue is full and the message is dropped, the scene task still catches up after it has handled the messages in hand). When a delete the user confirmed on the device could not be carried out (the scene did not close, the storage worker's queue was full, or the delete itself failed), it logs and posts the system notification `scene_delete_failed` (parameter: the scene name); the scene stays as it is and is not retried behind the user's back. Without a screen there is no runtime (headless). Its device events (`minute` for a new time zone, time format or synced clock, `battery`, `lang`) follow `PowerMonitor::supply()`, `SystemSettings::cell()` and `TimeSyncService::result_cell()` (attached before `start()`, as NetWiring is built after the runtime) on `wisp.bus`; the callbacks only set pending bits that the scene task takes on every step (after following the screen state), so a full scene queue delays a change but does not lose it. `stop()` releases the three subscriptions first, before the network is destroyed.
   **Network** (connectivity spec 4.1, `components/wisp_app/src/net_wiring.{hpp,cpp}`, after `PowerManager` and before the system duties and home screen): with a `Platform::random`, it constructs `net::PairingService`; if a Wi-Fi device with role `main` is registered, it also constructs `net::WifiService` and calls `init()` (which reads the saved networks and user enable flag, schedules the first attempt when enabled, or turns the radio off when disabled). `WifiService::tick()` and `PairingService::tick()` both run every 250 ms in a separate task `wisp.net`; a scan can block for about 3 s, so it cannot go into the shared `os::Timer` dispatch task, and boot therefore never waits for the network. On every loop the `wisp.net` task passes `PowerManager::level()` to `WifiService::set_power_level()` (it follows `PowerManager::level_cell()` on `wisp.bus` only to wake the task promptly, so a late wake never gets the level wrong): `deep_standby` turns off the hotspot, disconnects and turns off the radio (`hal::Wifi::set_radio(false)`); leaving `deep_standby` turns the radio on and reconnects immediately; `standby` leaves Wi-Fi alone. With a scene proxy, the same loop drives `net::NetworkWindow` before Wi-Fi (see the deep standby item of "Networking on the device"). With a `Platform::http_server` and a `WifiService`, it constructs `admin::AdminServer` (including the `WsHub`; this boot's identifier `boot_id` is generated once here with `Platform::random`, see connectivity spec 6.2). The `wisp.net` task starts the HTTP service when STA gets an IP or the hotspot opens, and stops it when both are down (the interface state is read from `WifiService::status()`/`ap_status()` on every loop; it follows `WifiService::wifi_cell()`/`ap_cell()` only to wake the task promptly, so a late wake never leaves the service in the wrong state); with `http_always_on` (the simulator) it starts at boot and does not stop when the network goes down. In addition, as long as the hotspot is open, the `wisp.net` task runs `Platform::captive_server` on port 80 (device only), with `AdminServer::captive_handler()` as the handler: any request arriving on the hotspot interface gets a `302` (other interfaces get 404) to `http://<hotspot address>:<http_port>/setup.html`, so that the phone's captive portal check opens the Wi-Fi setup page; it stops when the hotspot closes. A start failure is logged and retried with backoff while the interface is still up (from 2 s, doubling, up to 60 s). Each successful start prints a line `WISP_HTTP {"port": n}`. The boot report records `notes.net`. With a `Platform::sntp` and a `WifiService`, it constructs `net::TimeSyncService` (connectivity spec 5.6): on every loop the `wisp.net` task calls its `tick()` with "does STA have an IP"; when a sync is due, it reads `ntp_servers` in this task (from the settings cell, in memory) and then wakes the resident task `wisp.ntp` (4096 B stack, priority 3, `flash_access=false`) to do the SNTP request, set the system clock (`Platform::set_wall_clock`; on ESP it shares `wisp/port/esp/wall_clock.hpp` with the board's setting of the time from the RTC at boot), write the clock with role `main` and publish `system.time`. A request may block for a few seconds per server, so it must not hold up `wisp.net`.
   **Status shell** (scene device spec 5.3/5.5/5.6, `components/wisp_app/src/status_shell.{hpp,cpp}`): with a `SystemLayer`, after the network and before the system duties and home screen, it constructs `app::StatusShell` and calls `start()`. Its `device_status` is the same one `wisp.device.info()` uses (reads `PowerMonitor::last_status()` and `NetWiring::wifi_state()`, without touching flash), so it has to wait until the network objects exist; the time zone and the clock format are `utc_offset_min` and `time_24h` read from the settings cell (`SystemSettings::cell()`, memory only: the UI thread does not read Settings). It follows four state cells on the UI dispatcher (`UiRuntime`), so each callback runs on the UI thread: the scenes overview (`SceneRuntime::overview()`), the notice summary (`NotificationService::summary()`), the power level (`PowerManager::level_cell()`) and the Wi-Fi station (`WifiService::wifi_cell()`, when there is a Wi-Fi service). Each call refreshes: it re-reads `background_scenes()` and `unread_count()` (so one call that stands for several changes still shows the last), logs `status: background=<n> unread=<m>` when the counts change, and rebuilds the panel's model when the panel is open; a power level of `Standby`/`DeepStandby` closes the panel instead, also when the shell starts in standby (a cell's first call delivers its current value). The panel handlers: on open (logging `panel: open`) it builds the model from the current state. The header is `HH:MM` converted by `utc_offset_min` (`--:--` when the clock is not set), the battery and the Wi-Fi state, followed by the background scenes and the unread notifications (newest at the top). System notifications get their text from `ui::system_notice_text()` in the current UI language, with parameters substituted as they are (for scene notifications the parameter is already the scene name when posted); the holder of a wake-lock reminder first goes through `ui::holder_label()` (`scene.<id>` takes the scene's name: for a running scene (foreground or background) from `SceneRuntime::running_name()`, otherwise from the manifest in the repository, read on `wisp.fs` and cached in the shell, with one more refresh once it has been read; only when the scene is not installed is the id shown). On close it logs `panel: closed` (`PanelHandlers::on_close`). Tapping a scene row does `launch(id, User)`, and × does `exit(id)`; tapping a notification does `NotificationRouter::tap()`, × or a left swipe removes it with `dismiss`, an action button does `NotificationRouter::act()`, and "Clear all" does `clear_all()`. Banners are connected through `NotificationRouter::set_banner()`: the callback, on the thread that posted the notification (the scene task, in the case of `wisp.notify`), only posts the notification to the UI thread, where the text is generated and `show_banner()` is called; tapping does `tap()`. The router is still the notification service's only listener. Without a screen it is not built.
   **Firmware update service** (connectivity spec 6.5, constructed before the network, because the admin routes write the upload stream into it): `core::FirmwareUpdateService` wraps `Platform::firmware`. Without a UI it sets no confirmation callback (an upload is then rejected with `unavailable` at `begin`, since there is no screen to confirm on). The `wisp.net` task calls its `tick()` on every loop, and an unconfirmed image is discarded after 2 minutes.
5. **Finish**: records `boot_ms`, prints `"WISP_BOOT_REPORT <json>"` and then `"WISP_MANIFEST <json>"` (through `Platform::emit_line`), and then publishes the `system.boot.completed` event.
6. **Serial console**: with a `Platform::read_line`, starts the `wisp.console` task (see "Serial console" below).
7. **Confirm the image is good**: `FirmwareUpdater::mark_valid()`. On the device, if a newly installed image crashes or resets before this step, the bootloader rolls back to the old image (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`, see "Firmware and partitions" in `docs/porting-guide.md`); the simulator does nothing.

**Stop order** (`App::stop()`): serial console → status shell (`StatusShell`: releases its cell subscriptions (scenes overview, notice summary, power level, Wi-Fi; from this thread each release waits for a callback under way, so none runs afterwards) and removes the banner callback, then removes the panel handlers on the UI thread and waits for the jobs it posted earlier to finish; after that, banner callbacks still in flight and banner taps left in the system layer do nothing) → notification router (`NotificationRouter`: after unsubscribing, waits for the wake-ups it posted to the UI thread to finish) → voice (App first runs `Shell::set_conversation(nullptr)` on the UI thread; ## Devices: identity, roles and the generic path

Device model spec (`docs/superpowers/specs/2026-11-14-device-model-design.md`) sections 2-5.

- **Ids are names, roles are how code finds devices.** A board registers each device in `core::DeviceRegistry` under an id `<class>.<name>` it chooses; the id is the device's name in event topics, the boot report and the manifest. Portable code finds a device by interface and role, `registry.by_role<hal::Display>(hal::role::kMain)`, never by id. The board declares roles in caps `role` (a string or a list); the vocabulary is in `wisp/hal/roles.hpp`: `main` for the Display, Touch, Power, Clock, Imu, Wifi, AudioOut and AudioIn devices, `internal`/`removable` for storage, `power`/`talk` (and the `nav_*` roles) for buttons. Where this document names `display.main`, `power.main` and the like, it means the device holding that role (those are the simulator's and the reference board's ids). `tools/check_layering.py` rejects device-id literals in the portable components and `simulator/*.cpp`.
- **Interfaces.** `hal::Device::interface()` is a tag stored in the base class and set only through the typed interface classes (`hal::Display`, `hal::Button`, ...), so `get<T>()`, `list<T>()` and `by_role<T>()` compare it before a plain `static_pointer_cast`, without RTTI. One device object implements at most one typed interface. `DeviceClass` is the display category shown in the outputs; it must match the interface (`Wifi` is class `network`; a device with no typed interface, `None`, is class `other`).
- **`DeviceRegistry::add()` refuses** (the board records a failed device; boot goes on) a class that does not match the interface; a generic device whose id is not `<kind>.<name>` of at most 32 bytes; a second device with the same role in the same interface (for generic devices, the same kind, the id's prefix); caps that already carry `schema`; a schema that fails `hal::check_schema()`; a typed device that describes commands; a `Display` with any schema. At boot `App` warns about an interface among Display, Touch, Power, Clock, Imu, AudioOut, AudioIn and Wifi that has devices but none with role `main`, and about a key that holds both `power` and `talk` (holding it to talk also triggers the power key's long press).
- **The generic path.** A device no core service knows (interface `None`) describes itself with a `constexpr` `hal::DeviceSchema` (`wisp/hal/device_schema.hpp`): read-only properties and commands with typed arguments, ranges, units, defaults, `changes_state` and `min_interval_ms`. A typed device may describe read-only properties only. `hal::caps_of()` renders the schema into caps `schema` for the manifest and `GET /api/v1/devices`. `core::DeviceService` (`wisp/core/device_service.hpp`) is the one service in front of it: `list()`/`for_each()`, `get()` and `call()`, which validates the arguments, refuses commands on typed devices, checks occupancy, refuses a `standby: "off"` device while the screen is off (`Busy`), enforces `min_interval_ms` across all callers (`RateLimited`), runs the driver on the caller's task, warns once per command or property read over the 50 ms budget, caps a result at 1 KiB of JSON and logs `device <id>.<cmd> by <holder>` for each successful state-changing call. `App` constructs it next to `SensorService` and feeds it `PowerManager`'s level cell (its own subscription, released in `App::stop()` before the service goes). Its adapters are the agent's `device.list`/`device.call` (`components/wisp_agent/src/tools_device_call.cpp`) and the scenes' `wisp.device.list/get/call` (`components/wisp_scene/src/bind_device.cpp`; a scene reaches only the ids in its `permissions.device`, the agent's `lua.run` every device). The simulator's `haptic.main` (`wisp::port::sim::SimHaptic`, `components/wisp_port_sim/dev/sim_haptic.cpp`) is the worked example.

## Button input and standby

`hal::Button` declares `EdgeEvent` or `PollOnly` input (button-interrupt design sections 3–7). One `core::ButtonService` worker, `wisp.button`, consumes timestamped press/release records from a bounded `os::IsrQueue`; it reports edges only in task context. For every `down`/`up`/`short`/`long` it first calls its listeners (`ButtonService::add_listener()`), in registration order, with a `core::ButtonEdge` carrying the button id, the kind and the edge's own time (`os::now_us()` base: the confirmed edge, or for `long` the deadline, down + the long-press threshold, however late it was noticed), then publishes the `button.*` event, an observable copy that the bus may drop. Listeners run on `wisp.button`, on the fallback timer's task or on a `poll()` caller, never in an ISR, under the service's state lock: they only push into an `EdgeInbox`, store an atomic, update a cell, schedule a slot or make a non-blocking post (the hardware diagnostics' button test posts to the UI thread). `remove_listener()` returns only after a call in progress, so a follower removes its listener in its `stop()` while keys may still be pressed. `ButtonService::emit_for_test()` runs the same path without a button device. EdgeEvent input has no periodic poll: the worker blocks until an edge, mode change, debounce deadline (default 20 ms), or long-press deadline (default 1000 ms). Startup checks, event-driven wake maintenance and overflow level recovery are not periodic polling. Overflow is counted and logged with rate limiting, then the current level is resynchronised.

PollOnly input uses the active service interval (default 20 ms). `PowerManager` calls `set_standby(true)` for both screen-off levels and `false` on wake, rather than rebuilding a global 50 ms timer. Ordinary PollOnly buttons stop being read in standby/deep standby and cannot be relied on to wake the device. PollOnly `button.power` retains a 100 ms standby deadline; active cadence resumes on wake. `PowerManager` hears every edge through a listener that stamps the idle clock, sets an activity flag and, for any key but the power key once its owner has it, a wake latch, and moves a private counter cell; the cell's follower on the UI thread (`wisp.bus` headless) runs the activity callback, the undim and, with the screen off, the wake. A cell needs no free post-queue slot and no bus, and runs while the UI is paused, so a press in standby wakes the screen however full both are. The system duties hear the power key through a listener too, which pushes the key's `short` and `long` edges (only those) into an edge inbox (`power_key`) drained on the UI thread, which toggles standby or asks to power off, in edge order, with the bus flooded, the post queue full or the UI paused; an inbox overflow is counted in `mem` and logged. `shell::TalkKey` hears the talk key the same way: its listener pushes the key's `down` and `up` edges (only those) into an edge inbox (`talk_key`) drained on `wisp.bus`, and stores the last `up`'s time. The hold is timed from the `down` edge's own time, so a `down` handled late starts the hold as soon as it is handled if it is already 300 ms old (a late delivery adds no second 300 ms wait), and a short press handled late stays a press (no hold starts for a key the listener has already seen released, and an `up` less than 300 ms after its `down` drops a hold already begun); the capture ends when the `up` is handled, so a late `up` ends it late. A flooded bus loses no edge: they wait in the inbox, in order; when the inbox overflows and drops a press's `up`, the next `down` ends that press first (dropping its hold when the two `down`s, or the stored `up`, show the press was shorter than 300 ms). PMU battery/charging/VBUS sampling is independent: `PowerMonitor` remains at 1 s active / 30 s standby.

Failed edge attachment downgrades that device to PollOnly. Queue or worker creation failure uses an emergency polling Timer: its existing base tick (normally 20 ms) is deliberately retained across mode changes to avoid losing the only input path if replacement allocation fails. Device reads still obey 20 ms active / 100 ms power-standby deadlines and ordinary standby reads stop, but **this emergency path retains 20 ms scheduler wakeups**. It is not the normal EdgeEvent path. If even the fallback Timer cannot start, App records button-service failure and continues boot degraded.

The ESP port keeps digital ANYEDGE interrupts separate from an independent RTC IO high/low-level light-sleep wake channel (`rtc_gpio_wakeup_enable/disable` plus `esp_sleep_enable_gpio_wakeup`). Task-context wake maintenance holds a `button-held` no-light-sleep PM lock and disarms level wake while pressed; release rearms it. This does not add deep-sleep wake. Pins without independent RTC IO wake support, and unknown pre-existing GPIO ISR services whose IRAM flags cannot be established, fall back to PollOnly. The service is shared and never uninstalled by button teardown.

Quiescent detach disables/clears this pin, synchronously drains a task barrier on every enabled CPU, then removes the handler before freeing its context/sink. This covers the actual ISR core without guessing installer affinity; unicore uses the already-running local task. It assumes exclusive ownership of the pin (no concurrent external re-enable). Static ELF/IRAM closure checks and host teardown seams are evidence of implementation structure, **not** hardware cache-off, multicore ISR stress or sleep/wake acceptance.

The 4096-byte worker stack is non-hot and non-flash (`hot_stack=false`, `flash_access=false`), making it eligible for preferred PSRAM placement. The ESP port attempts an external stack only when configuration and available PSRAM allow it; external unavailability or task-creation failure falls back to internal RAM. Actual stack location and high-water mark remain pending `mem` acceptance. ISR queue storage, edge bindings and GPIO ISR context use `Mem::Fast` (internal RAM); PM locks and RTOS bookkeeping add overhead. Measure idle and the full STA+AP/two-httpd/WebSocket/TLS/OTA worst case with `mem`, including actual worker stack location/high-water mark, before claiming the existing `ram_budget.hpp` limits are met. The budget is not relaxed for this feature.

On 1.75C, `kUseSysOut=true` selects GPIO3 PWR EdgeEvent input by default after user-reported button-function tests on both boards and approval to merge. GPIO configuration/edge-service preparation failure selects the PMU fallback; a later sink failure downgrades the single registered GPIO device to polling. Functional acceptance does not establish electrical polarity measurements, reset strapping, battery-only RTC wake, worst-case RAM or standby-power results; those checks remain pending in the hardware document. The simulator supplies timestamp-preserving EdgeEvent input; it cannot validate physical wake or RAM consumption.

### State cells and edge inboxes

A component that others follow keeps its state in a `core::StateCell<T>` (`wisp/core/state_cell.hpp`) and its edges, which must all arrive, in a `core::EdgeInbox<E, N>` (`wisp/core/edge_inbox.hpp`). The primitives give three delivery paths; each topic's kind in `wisp/core/topics.hpp` names the delivery promise that topic is documented with:

| Path | Delivery | Lost when |
|---|---|---|
| Cell subscription | Coalesced: the callback converges on the latest value | Never |
| Cell mirror (bus event) | One event per change, in change order, published under the cell's lock | The bus is saturated |
| Edge inbox | Every edge, in push order | The consumer's dispatcher stalls for more than `N` edges (the oldest is dropped, counted and warned about) |

Delivery rules:

- A subscription's callback runs on the dispatcher it was given, never inside `set()` and never on the setter's thread unless that thread is the dispatcher. Its first call delivers the current value; a later call means "changed since the last call", and the callback reads whatever is current then. A -> B -> A between two calls delivers A again, so callbacks are idempotent. Calls of one subscription never overlap.
- An inbox run delivers only the edges waiting when it started and re-schedules itself if more remain; edges pushed by the handler are delivered in the next run.
- `set()` allocates only when copying `T` does.
- Lock order: cell -> the dispatcher's `schedule()` (and, for a mirror, the bus's publish lock); inbox -> `schedule()`. Callbacks run with no cell or inbox lock held. A callback may release any subscription, but releasing one that runs on another dispatcher blocks until that run returns.
- A callback never waits for another dispatcher: no `UiRuntime::run_blocking()`, no `EventBus::unsubscribe()` or `wait_idle()` from a callback. Releasing a subscription or destroying an inbox from another dispatcher's thread waits for its run, so such a wait can deadlock (a bus-dispatched callback inside `run_blocking()` while the UI thread releases that callback's subscription).
- Misuse (a cell destroyed with live subscriptions, an in-run cancel without a `finish`) aborts on the host and is logged on the device; after a reported misuse a cell's teardown waits at most 3 s, then aborts with a log line. An inbox destroyed from its own handler aborts on every build.

Who follows what: every component that follows another component's state subscribes to that owner's cell (AGENTS.md section 3, "State and events"); none folds a private copy from bus events. The only bus subscriber left on the device is the admin console's event forwarding (`admin::WsHub`). Scene lifecycle edges reach App through `SceneWiringDeps::on_lifecycle` (see the `scene.state` row): a mutex-guarded gate pushes them into one `EdgeInbox<scene::SceneTransition, 32>` (`scene_lifecycle`, drained on `wisp.bus`), whose handler moves a `running` scene to the front of the scene order, makes the order forget a `deleted` one and dismisses its notices, and hands every edge to the agent's scene tool index (`SceneToolIndexObserver::on_transition()`: `deleted` removes the scene's tools, every other state queues a manifest re-read on `wisp.fs`). The inbox is built before the scenes and, in `App::stop()`, the gate is closed and the inbox destroyed right after the network stops and before the agent goes; an edge after that (a delete still queued on `wisp.fs`) is dropped. Its 32 places hold the edges of many user actions (one to three each) and of every background scene restored at boot (at most `kMaxBackground`, one edge each); an overflow drops the oldest edges, is logged and shows in `mem` as `inbox scene_lifecycle overflows=<n>`. A dropped edge is not repaired later: for a lost `deleted`, the scene's notices stay until they are dismissed, its tools stay in the agent's index until the reboot, and its id stays in the scene order's file, which the scene list only uses to sort the scenes it finds installed; a lost `running` leaves the scene where it was in that order; any other lost edge skips one manifest re-read of the tool index, which the scene's next edge makes up for. No device-side component subscribes to `button.*`: `PowerManager`, the system duties' power key, `shell::TalkKey` and the hardware diagnostics' button test all listen to `ButtonService`.

Internal RAM: each cell, inbox and gate lock is an `os::Mutex`, whose RTOS mutex is in internal RAM (about 100 bytes), and a cell's body is where its owner is allocated. The whole state-cells phase is estimated at about 3.3 KB of internal RAM: 0.2 KB for the primitives (two locks) + 2.5 KB for the 14 cells above that existed before the edges (14 locks, about 1.4 KB, plus about 1.1 KB of cell bodies in the 12 owners allocated in internal RAM) + 0 for the followers (subscriptions are in PSRAM) + 0.6 KB for the edges (six locks: the three inboxes', `ButtonService`'s listener lock, `PowerManager`'s button activity counter cell, App's lifecycle gate; the inboxes themselves are in PSRAM). It is an estimate: it must be re-measured with `mem` on each board against `wisp/app/ram_budget.hpp` (`docs/backlog.md`, "State cell edges and cleanup: device checks not run").

Periodic work that remains, none of it re-reading state a cell carries: the `wisp.power` timer (`PowerManager::tick()` once a second: the idle clock, and the reminder for a wake lock held 30 minutes); the system duties' 100 ms UI timer (the setup and pairing cards' countdowns, which move no cell when they expire); the hardware diagnostics' 100 ms UI timer (sampler readouts, performance and RAM, the time sync row's synced time and each scene row's run state, none of which a cell holds; the network section's backoff countdown), its 1 s read of the live network values no cell carries (signal strength, saved networks), its 1 s storage measurement, a retry of a scene list it is still owed (1 s after a refused ask, 10 s after an unanswered one, only until one is shown), and the sampler's own reads of the power device and the clock (`wisp.sample`, above); the network loop (`wisp.net`, every 250 ms: it drives the Wi-Fi state machine and reads the level and supply itself, the cells only wake it); App's 2 s storage refresh (card hot-plug detection); `PowerMonitor`'s sampling (1 s, 30 s in standby); the PollOnly buttons' polling; the talk key's 20 ms hold timer while the key is down; the dev-mode scene watcher (500 ms, files on disk have no cell); and the screens' animation timers.

Dispatchers: `wisp.bus` by default. The UI runtime (`ui::UiRuntime`) is one too, for UI code. Its loop runs, in every iteration, the slots that were queued when the pass started (a slot re-armed during a pass runs in the next iteration). While the UI is paused it blocks indefinitely when no slot is queued, and paces itself with the loop period (10 ms) while one stays queued, so standby has no periodic UI timer.

The topic registry: `wisp/core/topics.hpp` is the one list of topic names. `tools/check_topics.py` (run by `tools/ci.sh`) checks it against the table above and forbids topic string literals in `components/` and `simulator/`. A registry row whose name contains `<` is a pattern (button topics are `<device id>.<edge>`). Prefix subscriptions and topics built from a device id are not checked by the script.

The `events` subscription of the admin console WebSocket (`admin::WsHub`, connectivity spec 6.2) forwards the topic prefixes `memory.`, `net.`, `power.`, `scene.`, `storage.`, `system.` and `todo.` (`kForwardedPrefixes`); `button.*`, `model.profiles` and `voice.state` are not forwarded, and `agent.state` and conversation deltas are pushed separately through the WS `agent` subscription (`AgentWsBridge`).

## Machine-readable output

The lines below that carry JSON are all "prefix + single-line JSON" (AGENTS.md section 4). When you change the field set of any of them, update `tests/smoke/sim_smoke.py`, `tests/smoke/admin_smoke.py` and this section with it.

- **`WISP_BOOT_REPORT <json>`** (boot flow step 5; `core::BootReport::to_value()`):
  ```
  {"board": string, "boot_ms": int, "fw": string,
   "devices": [{"id": string, "class": string, "state": "ok"|"degraded"|"missing"|"failed", "reason": string}, ...],
   "notes": {...}}
  ```
  `fw` is `Platform::firmware_version` (device: `esp_app_get_description()->version`, i.e. IDF's `PROJECT_VER`; simulator: the constant `"0.1.0"`). `notes` holds free-form diagnostic notes. The keys currently used: `mode` (value `"headless"`, without `display.main`), `storage` (value `"readonly"`, when mounting the internal flash fails), `library_roots` (string array from `core::StorageManager::roots(Area::Library)`; this field is how spec 9.2's "with `--no-sd`, Library has only the internal root" is verified in a machine-readable way), and `net` (connectivity spec 4.1, the network state at the moment of boot: `"missing"` means there is no `net.wifi` device (or the platform provides no `random`), `"off"` means there is no saved network, `"connecting"` means there is a saved network and it is connecting in the background).
- **`WISP_MANIFEST <json>`** (boot flow step 5; `core::DeviceRegistry::manifest()`):
  ```
  {"board": string,
   "devices": [{"id": string, "class": string, "model": string, "caps": {...}, "safe_area"?: {"x1","y1","x2","y2": int}}, ...]}
  ```
  The keys of `caps` differ by device class (see the notes in each `wisp/hal/*.hpp` header). `safe_area` appears only on entries whose `class` is `"display"` (spec 5.6). `class` is one of `display`, `touch`, `imu`, `power`, `clock`, `button`, `audio_out`, `audio_in`, `storage`, `network` and `other` (a generic device, which also appears with that class in `WISP_BOOT_REPORT`). Two caps keys may appear in any class: `role` (a string or a list of strings, on every device that has one; see "Devices: identity, roles and the generic path") and `schema` (on a device that describes itself — any class but a display — rendered from its `hal::DeviceSchema`; a driver never writes it). The simulator's haptic, as printed:

  ```
  {"caps":{"role":"main","schema":{"cmds":[{"args":[{"desc":"Duration","max":2000,"min":10,"name":"ms","type":"int","unit":"ms"},{"default":80,"desc":"Vibration strength","max":100,"min":0,"name":"strength","optional":true,"type":"int","unit":"%"}],"changes_state":true,"desc":"Vibrate once","min_interval_ms":100,"name":"pulse"},{"args":[{"desc":"Built-in effect number","max":123,"min":1,"name":"id","type":"int"}],"changes_state":true,"desc":"Play a built-in effect","min_interval_ms":0,"name":"effect"}],"props":[{"desc":"Motor running","name":"active","type":"bool"}]},"standby":"off"},"class":"other","id":"haptic.main","model":"sim-haptic"}
  ```

  `props` and `cmds` are lists in declared order; a parameter's `desc`, `min`/`max` and `unit` appear only when set, `choices` only on an enum, `max_len` only on a string, `optional`/`default` only on an optional argument. Each such device adds about 650 bytes to the line (the simulator's whole manifest is about 2.3 KB).
- **`WISP_PERF <json>`** (system duties; one line every 5 s from boot, whatever screen is in front; `SystemDuties::emit_perf_line()`):
  ```
  {"fps": number, "cpu": int, "flush_ms": number, "frames": int,
   "heap_internal_free": int, "heap_large_free": int,
   "wisp_fps": number, "wisp_ms": number}
  ```
  `fps`/`flush_ms` come from `ui::UiRuntime::perf()`. `flush_ms` is the average milliseconds the UI task spends on the screen per segment (one partial buffer), i.e. starting the transfer plus waiting for it to finish later; when transfer and rendering overlap, it is far smaller than the transfer itself. Both are essentially floating point, but integer values come back as `Int` rather than `Double` after a JSON round trip (`Value`/JSON tells Int from Double by the actual value, not the source type, see `tests/base/value_json_test.cpp`); parsers must not assume that any of these fields is always one particular JSON number form. `heap_internal_free`/`heap_large_free` come from `Platform::heap_info` (which may be empty, in which case both are 0). `wisp_fps`/`wisp_ms` come from `ui::wisp_perf()` (`wisp/ui/wisp_model.hpp`): over the last 5 s, the combined frame rate of all wisps (`WispView`), and the average milliseconds per frame: advancing the model and generating the shape, plus the time the wisp spends drawing lines and fills in LVGL's draw events (the software renderer rasterises inside these calls; flushing to the screen is not counted). With no frames in that period, both are 0 (mvp spec 6.1). E-paper produces a frame only when the expression changes, so `wisp_fps` is close to 0. The simulator's `--wisp-demo` cycles through the five expressions on its own screen (background black or white depending on the panel); combine it with `--panel mono|epaper` to see how monochrome and e-paper are drawn. The home screen stays behind it, and this line is printed as usual.

- **`WISP_BENCH <json>`** (the answer to the serial console commands `bench scroll [seconds]` and `bench drag [seconds]`; `wisp/app/bench.hpp`, registered through `Platform::console_commands` on both the device and the simulator):
  ```
  {"bench": "scroll", "fps": number, "frames": int, "ms": int, "cpu": int, "px": int}
  ```
  On the UI thread it takes the largest scrollable object on the current screen (the home screen does not scroll, so first open hardware diagnostics with the serial command `diag`; its list is the object), scrolls it by `px` (6) pixels every frame with `lv_obj_scroll_by_raw()`, reverses at each end, sends one `SCROLL_BEGIN`/`SCROLL_END` before and after, and scrolls back to the original position at the end. The default is 10 s; the command blocks until the measurement is done, the screen does not turn off automatically meanwhile, and it refuses to run while the screen is off. `frames` is the number of `REFR_READY`s, `ms` is the time from the first frame to the last, and `fps` = (`frames` − 1) / `ms`, to two decimal places; `cpu` is the average of `UiRuntime::perf()`'s `cpu_percent`, sampled once a second from the 2nd second of the run (the same meaning as `WISP_PERF`'s cpu: the wall-clock time spent inside `lv_timer_handler()`). This is how the raw column of the hardware document's "Performance baselines" section is measured, so the numbers can be compared directly with the baselines there.
  `bench drag` measures whole-page drag tracking (mvp spec 6.3):
  ```
  {"bench": "drag", "fps": number, "frames": int, "ms": int, "cpu": int, "px": int, "navs": int}
  ```
  It first brings the home screen to the front, then uses the command's own pointer input device (LVGL reads it just like a touch screen, so this goes through the shell's real drag path) near the top of the safe area, moving right by `px` (16) pixels per read from 1/8 of the screen width to 7/8, releasing to open the Settings page, waiting long enough for the slide animation, and then dragging back to the home screen the opposite way, and so on. `fps`, `cpu`, `frames` and `ms` mean the same as for `bench scroll` (frames during the pauses count too); `navs` is the number of times a new page was reached. At the end it returns to the home screen.
- **`WISP_HTTP <json>`** (network step; `NetWiring::reconcile_http()`): one line each time the admin console HTTP service starts successfully, `{"port": int}`, the actual port reported by `HttpServer::port()`. It may appear before `WISP_BOOT_REPORT` (with `http_always_on` it starts at boot). With the simulator's `--http-port 0`, the service is not started, so there is no such line; smoke tests that need the admin console pick a free port themselves and pass it in (`admin_smoke.py` retries with another port when the port is taken and the log shows `admin server failed to start`).
- **`WISP_REBOOT`** (simulator only, no JSON): printed when `Platform::reboot` is called (for example by `POST /api/v1/system/reboot`, or after a factory reset completes or a firmware update is confirmed). The main loop then returns, and the process ends with exit code 0 through the normal `App::stop()` (not by calling `exit()` directly on the timer thread, to avoid static destructors racing other threads). On the device it corresponds to `esp_restart()`.
- **`pair-code=<6 digits>`** (simulator debug command only, no JSON): the answer to the console command `debug pair-code`; `pair-code=none` when there is no valid pairing code. It is compiled in through `Platform::console_commands` only when the `wisp_sim` target defines `WISP_SIM_DEBUG_COMMANDS` (`simulator/main.cpp`); neither the portable layers nor the firmware have it. It lets `tests/smoke/admin_smoke.py` complete pairing without looking at the screen.

## Networking in the simulator

- `net.wifi` is `wisp::port::sim::SimWifi` (model `sim-wifi`): built in are `WispLab` (-45 dBm, password `wisp1234`), `Neighbor` (-70, `neighbor99`) and `OpenCafe` (-80, open). `--wifi-fail` makes every connection fail with `not_found`. The hotspot only changes state, and `ap_clients()` is always 1 while it is open. `set_radio(false)` disconnects and closes the hotspot, and scans and connections fail after that until `set_radio(true)`.
- The admin console is served by `SimHttpServer`, listening only on `127.0.0.1`, on port `--http-port` (default 8900, the same as the device's admin port; 0 means it is not started). The simulator has no captive portal service on port 80 (`Platform::captive_server` is empty). Outgoing requests (the model connection test `POST /ai/profiles/{id}/test`) go through `SimHttpClient` (libcurl, `find_package(CURL 7.80 REQUIRED)` in the host build; the portable layers must not include `curl/`).
- Touch scripts: `--tap X,Y@MS` (pressed for 100 ms) and `--swipe X1,Y1,X2,Y2@MS` (dragged within 400 ms, held for 200 ms, then released) inject a touch into `SimInput` MS milliseconds after the main loop starts; they can be repeated, with coordinates 0–479. Lines on standard input that start with `tap` / `swipe` (`tap X,Y` / `swipe X1,Y1,X2,Y2`) are also executed immediately, for scripts that need to wait for something to happen on the device before tapping: the smoke tests `factory_reset` and `firmware` wait until the confirmation dialog's log line appears in the WebSocket log, then tap "Yes" through standard input.
- Scene development (scene spec 6.4): `--scenes-dir <dir>` runs the scene repository in development mode with that directory as the code root, while data still lands in `<data-dir>/scenes/<id>/data`; the foreground scene reloads as soon as its files change. `--open-scene <id>` opens a scene right after `App::start()` returns. The debug command `debug scene-click <ref>`, available only when the `wisp_sim` target defines `WISP_SIM_DEBUG_COMMANDS`, clicks the widget in the foreground scene whose `ref` has that name (`SceneRuntime::click_ref()`) and answers `scene-click=ok` or `scene-click=<error>`. `debug scene-swipe <ref> <dir>` swipes `up`, `down`, `left` or `right` over that widget, reaching the nearest widget at or above it with `on_swipe` (`SceneRuntime::swipe_ref()`), and answers `scene-swipe=ok` or `scene-swipe=<error>`. `debug panel-tap <index>` taps the given row of the open pull-down panel (from 0, background scenes first, then notifications; `SystemLayer::tap_panel_row()`) and answers `panel-tap=ok` or `panel-tap=<error>`; `debug screenshot <path>` writes what is on the screen now as a PNG (the same as `--screenshot`, but available at any time) and answers `screenshot=ok` or `screenshot=<error>`. Standard output is flushed after every log line, so scripts reading the pipe (the smoke tests) are not held up by buffering. `--imu-script <file>` drives the simulated IMU from a script (`wisp/port/sim/imu_script.hpp`: `<milliseconds> tilt <x> <y> <z>`, `shake`, `flip`).
- Debug commands for voice, the agent and the shell (mvp spec 7.1, likewise compiled only under `WISP_SIM_DEBUG_COMMANDS`): `debug voice-text <text>` skips recording and ASR and hands the text to `ConversationController::voice_text()` as a spoken question (source `voice`; the reply is read aloud unless muted), answering `voice-text=ok` or `voice-text=<error>` (it refuses when there is no Wi-Fi, no `llm` profile, or while recording, speaking or running a turn); `debug clock-advance <seconds>` moves the simulated clock (`clock.main` and `Platform::wall_s`) forward and, like a time sync, publishes `system.time` `{"state":"synced","server":"debug","time"}` (through `TimeSyncService::note_external_sync()`, which moves only the result cell, not the service's status, so it never answers "Sync now"), so reminders catch up; it answers `clock-advance=ok` (`clock-advance=no time sync`, moving nothing, without a time sync service, as with `--disable net.wifi`). `debug banner-action <0|1>` presses the given action button of the current banner (for a to-do reminder, "Done" and "In 10 min"; `SystemLayer::tap_banner_action()`) and answers `banner-action=ok` or `banner-action=<error>`. `debug turn-steps` answers with the steps of the turn the home screen is showing (or the previous one): `turn-steps=<total steps>`, then for each kept step (oldest first) a space, the state (`ok`/`failed`/`running`), `:` and the label, for example `turn-steps=1 ok:添加待办 带伞` (the labels are in the current UI language; this example is Chinese, "Add to-do: take an umbrella"). `debug home-perf` answers what the home screen's refreshes that showed new turn text (the say text, the body and the layout after them, not the drawing) cost since it was last asked, and starts counting again: `home-perf=refreshes=<n> total_us=<us> mean_us=<us> max_us=<us>`; stream a long reply through `tools/fake_openai.py` and read it before and after to measure the per-refresh cost. The smoke tests `voice_turn`, `reminder` and `navigation` (`tests/smoke/sim_smoke.py`) use `tools/fake_openai.py` to replay model replies from `tests/smoke/*_script.json`, and simulate ASR and TTS (440 Hz PCM).
- Standard input has a single reader (`StdinReader` in `simulator/sim_stdin.hpp`, polling with a timeout, so it never gets stuck in a blocking read on exit): it reads whether or not `--headless` is given and whether or not stdin is a terminal. Touch lines go to the touch script; every other line is a serial console command, handed to the console task through `Platform::read_line`; the console has no `tap`/`swipe` command. Between `tap`/`swipe` and the coordinates there may be spaces or tabs. When stdin is the controlling terminal and the process is in a background process group (`wisp_sim &`), the reader pauses and resumes after `fg`; the simulator ignores `SIGTTIN`, so job control does not stop it.
- Signals: `SIGINT`/`SIGTERM` make the main loop return as for a reboot, ending with exit code 0 through the normal `App::stop()` (SDL's own signal handling is turned off with `SDL_HINT_NO_SIGNAL_HANDLERS`, otherwise headless mode would not receive them). Handling is one-shot: if shutdown hangs, sending the signal again ends the process the default way.

## Networking on the device

- `net.wifi` is `wisp::port::esp::EspWifi` (`components/wisp_port_esp/net/esp_wifi.cpp`), registered last by the board's `init()`, which also turns the radio on there (`Platform::random` depends on it). The driver configuration is kept in RAM only (`WIFI_STORAGE_RAM`), and saved networks are managed only by `WifiService`. `link()` reads the snapshot maintained by the event callback. Disconnect reasons are mapped by `wifi_reason.hpp`, and a handshake failure counts as `auth_failed` only when the signal is good enough (RSSI ≥ -75 dBm); when the disconnect event carries no RSSI, the strongest signal of the network with the same name in the latest scan within two minutes is used instead, and if there is none it does not count. Hotspot: AP+STA, WPA2-PSK, channel 1, at most 4 clients. While the hotspot is closed, the AP interface keeps a hidden WPA2 placeholder configuration with a random password, so the moment it switches to AP+STA it never broadcasts an open network. At the same time a captive portal DNS runs on UDP port 53 of the hotspot address (`net/captive_dns.cpp`, which answers every A query with the hotspot address). The first time STA gets an IP, mDNS starts: `wisp.local`, advertising `_http._tcp` on port 8900.
- The admin console is `EspHttpServer` (`esp_http_server`): port 8900, at most 7 connections (`lru_purge_enable`; every request marks the open WebSockets as recently used, so when connections are full, idle keep-alive connections are closed first). The upgrade of `/api/v1/ws` is handed to `WsHandlers::on_open` before the handshake (`CONFIG_HTTPD_WS_PRE_HANDSHAKE_CB_SUPPORT`), and a refusal is a plain 403. Task priority 3, below the UI. The captive portal on port 80 is a second instance (another control port, 4 connections, no WebSocket); `AdminServer::captive_handler()` redirects only requests on the hotspot interface and returns 404 for the rest. The interface a request arrived on is judged from the connection's local and peer addresses (`net_iface.hpp`), not from request headers.
- Outgoing requests go through `EspHttpClient`: HTTPS is verified with the IDF certificate bundle (including the host name), redirects are not followed, and response bodies are limited to 64 KB.
- Deep standby (scene device spec 4.1, 4.4): `EspWifi::set_radio(false)` is `esp_wifi_stop()`, and `set_radio(true)` is `esp_wifi_start()`. While the radio is off, `Platform::random` does not give true random numbers, but no pairing codes, tokens or hotspot passwords are generated in that time (they all need a network client or the screen on). The old `net/idle_off_min` (disconnect after 10 minutes in standby) has been removed, and stored values are no longer read. Scene requests made during deep standby go into `SceneHttp`'s deferred queue (4 per scene; beyond that `deferred_queue_full`; queued for more than 1 hour, `deferred_timeout`; they still count towards the 30-per-minute limit when submitted). `net::NetworkWindow` is driven by the `wisp.net` task: on entering deep standby, or 15 minutes after the previous window ended, and only when the queue is not empty, it takes the `network` lock of `system.netwindow` (log `netwindow: open`), so `PowerManager` goes back to `standby` and Wi-Fi turns on and reconnects. Once connected, it releases the queue, and frees the lock when the queue is empty and one time sync attempt has finished (the attempt count of `TimeSyncService::result_cell()` moved; waiting at most 30 seconds after connecting) (`netwindow: closed (done)`); if it cannot connect within 60 seconds, `closed (no wifi)` (if the connection drops midway through the window, the requests are queued again and it waits another 60 seconds from the drop); after a full 5 minutes open, `closed (timeout)`; if woken meanwhile, `closed (awake)`. Once the lock is released, the device goes back to deep standby and Wi-Fi turns off; requests not sent stay queued, and when queueing starts, requests in the run queue that have not started yet also go back to the deferred queue. Wi-Fi starts reconnecting only on leaving deep standby (the screen turning on, or another `network` lock bringing the device back to `standby`), so the queue waits until STA is connected, at most 60 seconds, before it is released; requests submitted while it is being released queue behind the backlog, and do not get `rate_limited` because the run queue is full.
- System wake locks (scene device spec 4.3; while held, the device does not enter deep standby). An open admin page takes none: neither its WebSocket nor its REST requests keep the device awake, so with the screen off deep standby still turns Wi-Fi off and the page reconnects once the device wakes. A half-open WebSocket is still closed so it does not hold a client slot: `WsHub` sends each client `{"t":"ping"}` every 30 seconds, the page answers `{"t":"pong"}`, and after 3 rounds with no message at all from a client it closes it (log `client N closed: silent`); ESP's httpd also has TCP keepalive on (probing every 10 seconds after 30 seconds idle, disconnecting after 3 unanswered). The locks are `system.upload` (`network`, from the start of a scene zip upload to its end or abort), `system.ota` (`network` + `cpu`, firmware upload and write), `system.ntp` (`network`, during each time sync attempt of `wisp.ntp`), `system.hotspot` (`network`, while the setup hotspot is open, held by the `wisp.net` task) and `system.netwindow` (`network`, the network window).
- Web assets: at firmware build time, `tools/pack_assets.py` packs `web/` into `wisp_web.wpak` (the build fails if it exceeds 256 KiB or the 170 KB gzip budget), which is linked into the app image with 4-byte alignment (`target_add_binary_data` in `firmware/main/CMakeLists.txt`, symbols `_binary_wisp_web_pack_start/_end`), and static files are sent directly from the mapped flash. So the web pages and the firmware are always the same version and switch together with OTA, and there is no longer a separate `assets` partition.
- Firmware upload (connectivity spec 6.5): the request body of `POST /api/v1/system/firmware` is not buffered. `EspHttpServer` hands it to `FirmwareUpdateService` in 4 KB chunks through `HttpServer::StreamHandler`, and `EspFirmwareUpdater` writes it with `esp_ota_*` (sequential writes) into the `ota_N` slot that is not running. `FirmwareUpdateService` collects the received data into a 32 KB (`kIoChunk`) PSRAM buffer; when it is full or the request ends, it hands it to `wisp.fs` to write through `StorageWorker::run_sync(…, IoLane::Bulk)`, and waits for that chunk to be written (at most 10 s) before accepting the next. `begin`, the final verification (`finish`, at most 30 s), `activate`, `mark_valid` and `abort` (queued, not waited for) also run on `wisp.fs`; httpd only does the network I/O and the waiting. If a chunk times out, the upload fails with `write_failed`; when that chunk runs late it still holds its own buffer, and the `abort` queued after it runs after it. As soon as the first 336 bytes have arrived, the project name `wisp`, the chip (`CONFIG_IDF_FIRMWARE_CHIP_ID`) and the board name descriptor (see "Firmware and partitions" in `docs/porting-guide.md`) are checked, and a mismatching image does not get a single byte written. Web upload never requires a signature. httpd has only one task, which brings a few known limitations (accepted as they are, not worked around in code): WebSocket log push pauses until the upload ends; when answering early, if more than 8 MiB of the request body remains (`kBodyDrainBytes`), it is no longer read and discarded, and the connection is reset straight after the answer is written (for example the 413 for a file over 8 MiB), so the browser mostly sees "cannot connect" rather than `payload_too_large`; a second upload started at the same time does not get a 409 immediately, but queues behind the first one and gets 409 `busy` only after the first one ends (and is waiting for confirmation) and its own request body has been read and discarded; `stop()` has to wait for an upload in progress to end (when the client stops sending, at most two 5 s receive timeouts). The simulator has one thread per connection, so in all these cases it answers immediately.

## Serial console

- Connectivity spec 8.2: command parsing is in the portable layer (`wisp/app/console.hpp`: `split_command()`, `run_command()`), and reading input is in the platform layer (`Platform::read_line`: waits at most `timeout_ms` and returns `Line`/`Timeout`/`Closed`). The console runs on its own `wisp.console` task (commands that may block for a few seconds do not hold up the UI thread); `App::start()` starts it last and `App::stop()` stops it first.
- Commands: `help`; `wifi status` (`state=… ssid="…" ip=… rssi=…`, plus `reason=…` in Backoff; then one line `saved ssid="…"` per saved network, with ` auth_failed` added for those whose password was rejected; and, while the hotspot is open, a line `ap ssid="…" clients=n`); `wifi add <ssid> [password]`; `wifi forget <ssid>`; `wifi ap on|off`. Arguments containing spaces use double quotes, with `\"` and `\\` as escapes inside the quotes; `hex:<bytes>` gives the SSID as hex bytes (matching the API's `ssid_hex`). SSIDs in the output are always double-quoted, with control characters and invalid UTF-8 bytes written as `\xNN`; `diag [close]` (opens or closes hardware diagnostics on the screen, answering `ok`; mvp spec 6.6).
- Secrecy: the console does not echo input and does not write input lines to the log (output goes through `emit_line`, not `WLOG`), and no output contains the Wi-Fi password, the hotspot password, the pairing code, tokens or API keys (the only exception: `debug pair-code` in the simulator's debug build prints the current pairing code, see machine-readable output above). `wifi ap on` prints only the hotspot SSID and address; the password is shown only on the screen. The terminal program's own local echo is beyond the device's control.
- Platform extensions: `Platform::console_commands` appends platform-specific commands (listed at the end of `help`; they cannot override built-in commands), for example the simulator-only debug command `debug pair-code`.
- Platform commands: the device has `mem` (each heap and each task's stack, `wisp/port/esp/mem_report.hpp`; then one line `bus dropped=<n> cell_subs=<n>`: events the bus dropped and live cell subscriptions, followed by one line per edge inbox, `inbox <name> overflows=<n>` (edges it dropped since boot: `inbox scene_lifecycle`, App's scene lifecycle edges; with a screen `inbox power_key`, the system duties' power key; with a talk key and the voice running `inbox talk_key`, `shell::TalkKey`; see "State cells and edge inboxes"), from `App::dispatch_report()`; then one line per storage worker and lane, `wisp.fs` first: `storage <worker> <interactive|normal|bulk> jobs=<n> wait_max_ms=<w> job_max_ms=<j>`, the longest queue wait and the longest job since boot rounded up to whole milliseconds, from `StorageWorker::stats()`; `storage wisp.sd.io off` without an SD I/O worker; `app::storage_report()`) and `sleep [reset]` (light sleep in deep standby: the running and the last session, kept across a chip reset, and the PM locks; `wisp/port/esp/sleep_stats.hpp`); both the device and the simulator have `bench scroll|drag [seconds]` (`WISP_BENCH`, see machine-readable output above); the simulator's debug build also has `debug …` (next item).
- Device: `wisp::port::esp::EspConsole` (`components/wisp_port_esp/console_esp.cpp`) installs the USB-Serial-JTAG (or UART) driver and routes the VFS through the driver, with log output working as usual; `read_line` uses the driver's read with a timeout, without busy-waiting.
- The `--screenshot` capture (`UiRuntime::take_snapshot`) includes the active screen and `lv_layer_top()` (the confirmation dialogs, the Wi-Fi setup card and the pairing card are all on this layer), but not `lv_layer_sys()`.
- Firmware upload: `wisp::port::sim::SimFirmwareUpdater` writes the uploaded image to `firmware.bin` in the data directory, with target board name `simulator`, any chip, and a capacity of 5 MB. After confirmation it reboots as usual (`WISP_REBOOT`), but the simulator cannot run ESP images, so after the reboot it is still the original version (the web page shows it as rolled back). The version number comes from `cmake/wisp_version.cmake` (the same rule as the firmware, see `docs/porting-guide.md`).
- Web assets: at build time, `tools/pack_assets.py` packs `web/` into `assets.wpak` next to `wisp_sim` (when `web/` does not exist it packs an empty directory, providing only the API); `--web-dir <dir>` instead packs that directory in memory at startup, by the same MIME/gzip rules (`wisp::port::sim::pack_web_dir()`).
- Vector font image (vector font spec 3.3): at build time, `tools/pack_font_image.py` packs `components/wisp_ui/fonts/noto_sans_cjk_sc_subset.ttf` into `fonts.bin` next to `wisp_sim`, which is read whole into memory at startup and handed to `Platform::font_image`; `--font-image <path>` uses another file, and `--font-image none` loads nothing (large text uses the bitmap font instead). On the device, `app_main` maps the `fonts` partition (`wisp::port::esp::map_font_partition()`). Both are validated by `UiRuntime::start()` with `ui::open_font_image()`, and a failure only degrades.
- 16 px body-text bitmap font image (glyph partition spec 3.3): at build time, `tools/pack_glyph_image.py` packs `components/wisp_ui/fonts/lv_font_cjk_16.c` into `glyphs.bin` next to `wisp_sim`, which is read whole into memory at startup and handed to `Platform::glyph_image`; `--glyph-image <path>` uses another file, and `--glyph-image none` also turns off the host's built-in CJK 16 fallback (`builtin_glyphs = false`), to see in the simulator what a device without the `glyphs` partition looks like. On the device, `app_main` maps the `glyphs` partition (`wisp::port::esp::map_glyph_partition()`). Both are validated by `UiRuntime::start()` with `ui::open_glyph_image()`, and a failure degrades along the fallback chain of glyph partition spec 4.3.

## Logical storage areas

`core::StorageManager` (`enum class Area { System, Library, Backup }`):

| Logical area | Root list | Quota |
|---|---|---|
| `System` | `[<int>/system]` | — |
| `Library` | SD online: `[<sd>/wisp/library, <int>/library]`; otherwise: `[<int>/library]` | `<int>/library` defaults to 3 MiB (`StorageConfig::internal_library_quota`); beyond it, `QuotaExceeded` is returned; the SD card layer has no quota |
| `Backup` | SD online: `[<sd>/wisp/backup]`; otherwise: `[]` (unavailable) | — |

Writes always go to the first root in the list; reads enumerate all roots in order. Mount points on the device: the internal flash (LittleFS) at `/int` and the SD card (FAT, 1-bit SDMMC) at `/sd`; in the simulator, `<data-dir>/int/` and `<data-dir>/sd/`. For atomic writes (`write_atomic`) and the pitfall that `rename` on FAT cannot overwrite an existing file, see `AGENTS.md` section 8.

All internal flash reads and writes run on one thread, `wisp.fs` (`core::StorageWorker`), the only task that declares `os::TaskConfig::flash_access = true` (AGENTS.md section 5). File work that touches only the SD card runs on a second worker, `wisp.sd.io` (when the board has a card slot); `core::StorageRouter` picks the worker by `core::Medium`, and sends card work to `wisp.fs` when there is no `wisp.sd.io`, before it starts, or once it has been joined. `wisp.fs` may touch the card too; `wisp.sd.io` never touches internal flash and never waits for `wisp.fs`. Other threads hand work over through `submit()` (returns once queued) or `run_sync()` (queues and waits; on the worker's own thread, or in the single-threaded boot/shutdown phases, it runs in place). Each worker has three lanes in priority order, each first-in, first-out, with no order across lanes or workers (a producer that needs two jobs in order waits for the first):
- **Interactive** (16 on `wisp.fs`): short jobs someone waits for. Settings saves and `flush()` (`CachedSettingsBackend`, and `SettingsFront`'s direct calls when there is no cache), conversation appends (`AgentDeps::run_io_interactive`), the memory and todo tools (`ToolThread::FsInteractive`), the admin console's note and todo deletes, the reminder pass of `ReminderScheduler` and the todo buttons on its notifications.
- **Normal** (32): other JSON documents (notifications, Wi-Fi, pairings, model profiles, scene order), scene data and listings, the boot loads (settings, conversation, memory, todos), conversation archive and clear, the factory reset, scene install and export, and the agent's scene file tools (on `wisp.sd.io` for files on the card).
- **Bulk** (4): firmware chunks and file download chunks, at most `kIoChunk` (32 KB) each.

A lower lane that has waited behind `kLaneTurnAfter` (8) higher jobs gets one forced turn, and two forced turns never run back to back. So besides the job running when it was queued, an Interactive job waits for at most one forced lower job, a waiting Bulk job runs after at most 9 jobs and a waiting Normal job after at most 10. On `wisp.fs` the running job and the forced one may each also wait for one card operation on a card lock (`SceneFiles` takes its card lock for every scene not loaded as Internal, a new scene's first call included), so an Interactive job's worst wait there is two jobs plus two card operations. Each lane counts its jobs and its longest wait and job (`LaneStats`, `StorageWorker::stats()`), which `mem` prints. `wisp.sd.io` (`StorageWorker::sd_io_config()`) has the same three lanes with room for 1, 16 and 4 jobs. When the Interactive lane is full a settings save goes to the Normal lane (it writes whatever is dirty when it runs, so order does not matter); callers that wait retry for up to 2 s and then report busy, as before. Before a restart, power-off or deep standby `App::flush_storage()` drains both workers, every lane included. Any thread that leaves this path and touches internal flash or the card directly is stopped by `WISP_ASSERT_FLASH_THREAD`/`WISP_ASSERT_SD_IO_THREAD` (`wisp/os/flash_guard.hpp`): in the simulator and unit tests it prints the call site and then `abort()`s; on the device each call site logs `WLOG_E` once and does not abort on its own.

Both media go through `core::StorageManager`, which tells them apart by `core::Medium` (`Internal`, `Sd`): `medium_of(path)` says which one a path is on, and `has_sd()` whether the board registers a `Storage` device with role `removable` (a card slot, whether or not a card is in). Each call checks the thread rule of its path's medium (`WISP_ASSERT_MEDIUM_THREAD`: the flash rule for `Internal`, the SD rule for `Sd`) and takes that medium's I/O lock, so card I/O never waits for a flash erase; the locks nest `int_io_mu_` before `sd_io_mu_` before `state_mu_`. A path that does not normalize is `InvalidArgument` before any thread check, on any thread, and a `rename()` from one medium to the other is refused. `core::StorageRouter` (`App::storage_router()`) is the one place that picks the worker: `Medium::Sd` to `wisp.sd.io` from its start until it has been joined (`StorageWorker::joined()`), everything else to `wisp.fs`. While `stop_sd()` lets `wisp.sd.io` finish its queue, new card work is refused (`submit()` false, `run_sync()` `Busy`) rather than sent to `wisp.fs`, where it could overtake the card jobs still queued; a card job refused because `wisp.sd.io` has been joined meanwhile goes to `wisp.fs` once; a full lane is reported to the caller, never moved to the other worker. Called from a job on `wisp.sd.io`, `Medium::Sd` runs inline. `wisp.fs` may wait for `wisp.sd.io` only while it holds no card lock (`StorageManager`'s `sd_io_mu_`, `SceneFiles`' card lock), since the card job could be waiting for that lock.

Scene code and data do not belong to the three logical areas above. They live at `<int>/scenes` under the internal root (`core::SceneRepository`; for development mode, see `--scenes-dir` in the "Networking in the simulator" section above): each scene is `<int>/scenes/<id>/`, its data is in the `data/` subdirectory inside it, and the files of `wisp.files` are in the `files/` subdirectory (on the first write, depending on the `files` declaration in `scene.json`, they may go to `<sd>/wisp/library/scenes/<id>/files` instead; the location is recorded in `data/files_loc.json` and does not change after that; see `SceneFiles` in the "Scene runtime" section below). Replacing a scene is a directory-level two-stage rename, not a single-file `write_atomic`; see the "Scene runtime" section below.

## Scene runtime

Scene spec 3/6. For the tasks, see the "`flash_access` declared by each task" table at the end of "Boot flow" above; for the start and stop order, see the body text of the same section.

### Background scenes, memory budget and restore at boot

Scene device spec 3; implemented in `scene::SceneRuntime` (the file header of `components/wisp_scene/include/wisp/scene/scene_runtime.hpp` describes the full lifecycle).

- Slots: all scenes share the single task `wisp.scene`, with at most one in the foreground and three in the background (`SceneRuntimeConfig::max_background`). Each slot has its own instance number, VM, timers, minute tick and `SceneStore`; a scene keeps its instance number when it moves between foreground and background. Each step still has its own 200 ms budget, and the scene in front's work runs before background work ("Message flow", lanes), so background scenes cannot hold up the foreground.
- Transitions: for a scene whose `scene.json` declares `"background": true`, the back gesture, `close()`, `wisp.scene.close()`, and opening another scene while it is in the foreground all move it to the background (`on_hide` → release the wake locks it holds → take down the view and return to the original screen → `scene.on_state("background")`). The VM, storage, timers and declaration tree are all kept, and UI changes only update the declaration tree without being sent to the UI thread; scenes without the declaration close as before. Opening it again (from the list, a row in the panel, or a tapped notification) rebuilds the view from the declaration tree (`SceneInstance::rebuild()`), then calls `on_show` and `scene.on_state("foreground")`. `exit()`, the × in the panel, `wisp.scene.exit()` and the admin console's `POST /scenes/{id}/exit` always close it completely. The `scene.state` event sends `background` for the background and `running` for the foreground.
- Timers: for scenes that declare `background` (whether in the foreground or the background), timers and the minute tick keep running while the screen is off; for other foreground scenes they pause while the screen is off, and on screen-on each missed timer fires once.
- APIs not available in the background (spec 3.4): `wisp.sensor.subscribe`/`on` and `wisp.power.keep_screen_on` return `nil, "not_in_background"`; existing sensor subscriptions pause on moving to the background and resume on returning to the foreground.
- Memory budget and eviction (spec 3.5): all VMs allocate from the same `VmPool`, with a total budget of `scene::kVmBudgetBytes` (3 MB). A single VM is still capped at 2 MB, which is also the amount the foreground is guaranteed to get; an allocation beyond either fails as a memory error. When a scene opens, comes back to the foreground or moves to the background, and before every message while a scene is in the foreground, background scenes to close are picked in "longest since last in the foreground" order: first those beyond the count limit, then those that make the background total exceed `budget - 2 MB`. An evicted scene gets `on_close` and is flushed as usual, with the log `<id>: evicted (...)` and a system notification.
- Restore at boot (spec 3.6): the ids of the background scenes (longest since last in the foreground first, plus boot launches still loading) are written to `scenes/background.json` in the System area (`{"ids": [...]}`, `write_atomic`, on `wisp.fs`) every time they change. It is written only after `restore_background()` has read it, and scenes closed by `stop()` are not removed from the list, so they are restored at the next boot too. After `system.boot.completed`, they are started one by one in the background with `launch(Boot)`: build the VM, run the entry file and build the declaration tree, without building a view or calling `on_show`; `wisp.scene.launch()` is `"boot"`. A scene that fails to start is skipped, logged, gets a system notification, and is removed from the list.
- Tapping a notification (spec 5.1): `SceneRuntime::deliver_notification()`. A foreground scene stays in the foreground, a background scene comes back to the foreground, and a scene that is not running is opened with `launch(Notification)` (`wisp.scene.launch()` is `"notification"`); once the scene is in the foreground, `scene.on_notification(id)` is called.
- Data migration (spec 7.3): when the data version is lower than the manifest's `schema_version`, `scene.migrate(old_version)` is called after the entry file has run and before the UI is built, with a time limit of 2 seconds (`scene::kMigrateMs`). Writes to `wisp.store` made by the entry file and during migration go into the same batch: on success they are committed together with the new version number; on an error or a timeout the whole batch is discarded and the data is left untouched, with an error message starting with `migrate failed: `. When the data version is higher than the manifest's, opening is refused (`data version <n> newer than scene <m>`).

### Message flow

- The `wisp.scene` task runs one step at a time, each with its own 200 ms budget: a `SceneMessage` (body in PSRAM), a call result, a due timer callback or a slice of the agent's `lua.run` (`kLuaRunSliceMs`, 200 ms). After each step the scene's reactive state is refreshed once, and the resulting changes are collected into one batch for `PatchQueue`.
- Lanes (scene-runtime-core spec 3.1): before each step the task picks from (1) the message queue, one message in arrival order; (2) the scene in front, its oldest result, else one of its due timers; (3) the background and headless scenes and the agent's `lua.run`, round-robin. After `kQueueBurst` (8) messages in a row one waiting lane item runs, and after `kFrontBurst` (4) front items in a row one waiting back item runs, so with the queue and the front both saturated a waiting back item runs after at most (8 + 1) × 4 + 8 = 44 items. Within one VM a waiting result runs before a due timer already taken.
- Messages come from three places: the UI thread (widget events), `wisp.fs` (receipts for completed package and storage loads), and `SceneHost` requests (open/close/delete, with instance number 0, identifying the scene by id), plus `Completed` wake-ups. Call results (`wisp.http`, `wisp.http.download`, `wisp.files`) do not travel in messages: each VM (scene slot, or the agent's `lua.run` VM) has a `CompletionBox`, a fixed ring of `kMaxCallsInFlight` (16) entries in `Mem::Large`. Its producers (`wisp.shttp`, `wisp.shttp.dl`, `wisp.fs`, and the scene task itself for refusals made inside a call) put results there and queue a `Completed` wake-up, so no result of a live VM is ever dropped; a result for a closed or faulted VM is freed and counted in `stale_dropped()`, and a result that cannot be kept for lack of memory still runs its callback once, with the error "other" (`wisp.http`) or "no_memory" (`wisp.files`). A VM may have at most `kMaxCallsInFlight` calls waiting for results (HTTP, downloads and files together); one more raises the Lua error "too many calls waiting for results (at most 16)", which `pcall` catches, and a place frees as soon as the call's result has run. Every message carries an instance number, and messages whose instance number is not the foreground scene's current one are dropped (`stale_dropped()`), so messages for a scene that has closed cannot affect the next scene opened.
- The message queue capacity is 64 (`SceneRuntimeConfig::queue_capacity`). Each frame, the UI thread's frame hook applies at most 64 operations from `PatchQueue` (`per_frame` of `PatchQueue`) to the `SceneView` of the matching instance. When a large batch update is spread over several frames, the frames in between show a half-updated picture the scene was never really in, and the next frame completes it.

### `/int/scenes/` layout and two-stage replacement

`core::SceneRepository` (`components/wisp_core/include/wisp/core/scene_repository.hpp`):

- Layout: under `<code_root>/<id>/` are `scene.json`, the entry file, `lib/**/*.lua` and `assets/**`. The scene's data is in `data_dir(id) = <data_root>/<id>/data` and its files in `files_dir(id) = <data_root>/<id>/files` (treated the same as `data/`: not part of the package, not included in `load()`, export or `code_bytes`, moved along with `data/` on replacement, kept by `remove()` without data, and deleted with data together with `<sd>/wisp/library/scenes/<id>` on the SD card). On the device and in the simulator outside development mode, both roots are `<int>/scenes`, so the data directory lands inside the package directory; in the simulator's development mode (`--scenes-dir`), the code comes from the working directory and the data is kept elsewhere.
- Replacement (install/upgrade) is atomic across power loss, using the directory version of the "two-stage naming" in AGENTS.md section 8:
  1. New files are written into `<code_root>/.<id>.tmpdir/`;
  2. that directory is renamed to `.<id>.newdir`; from this step on it counts as complete;
  3. if the old `<id>/data` and `<id>/files` exist, they are moved into `.<id>.newdir` (if either already exists on both sides, the whole replacement is abandoned and neither side is deleted);
  4. `<id>` is deleted;
  5. `.<id>.newdir` is renamed to `<id>`.
  `recover()` (run once on `wisp.fs` at startup, see boot flow step 3) discards every `.*.tmpdir`, and takes every `.<id>.newdir` through steps 3–5. The staging names end in `dir` because `StorageManager` reserves names ending in `.tmp`/`.new` for its own single-file atomic writes.
- Threads: the parts that touch files all run on the flash thread `wisp.fs` (`SceneRepoConfig::worker`). When called on another thread (the admin console's httpd, delete confirmation), a method queues that part to `wisp.fs` and waits until it is done; on `wisp.fs` itself, or with no worker (boot phase, tests), it runs in place. The reads `manifest()`, `info()`, `manifests()` and `list()` take one job per scene (a long listing never holds the worker for more than one scene's files) and parse `scene.json` on the caller, or in the job with `core::ParseOn::Worker`, which the admin console's routes use because the httpd task's stack is small; each scene is a snapshot of its own, and `changed_since()` says what changed meanwhile. `load()`, export, `recover()`, the install swap and `declared` parse in their job. The agent tool `scene.list` runs on `wisp.agent` (it waits for the per-scene jobs), the shell's scene list on `wisp.shell.list`. Validation, the source compile check and `before_replace` of `install()` (closing the scene, which may wait several seconds for the scene task) stay on the calling thread. Staging (step 1) is split into several jobs of at most 32 KB each (`kIoChunk`) without holding the repository lock (`.<id>.tmpdir` belongs only to this install); only the final swap-in (steps 2–5) holds the lock, as one job. `export_zip()` first lists the files in one job, then reads them one by one in chunks of at most 32 KB; if a replacement or delete lands meanwhile (the repository's generation changes), the export fails with `Busy` rather than mixing two versions. So other jobs (settings persistence, download chunks) wait for at most one chunk.

### `SceneFiles`: private files of a scene

`core::SceneFiles` (`components/wisp_core/include/wisp/core/scene_files.hpp`) is the service behind `wisp.files` and `wisp.http.download` (scene device spec 7.1/7.2; Lua bindings `bind_files.cpp`, `bind_http.cpp`).

- Location: decided on the first write (`write`/`append`/download) by the `files` declaration in `scene.json` (`SceneManifest::files`, provided by `SceneRepository::manifest()` through `SceneFilesConfig::declared`): `"auto"` (the default) uses `<sd>/wisp/library/scenes/<id>/files` when the SD card is online (quota 64 MB), and `<int>/scenes/<id>/files` otherwise (quota 512 KB); `"sd"` uses only the SD card and returns `unavailable` without a card, never falling back to internal storage; `"int"` always uses internal storage. It is recorded in `data/files_loc.json` (`{"location":"sd"|"int"}`, `write_atomic`) and does not change after that: if the declaration changes later, the record wins and the files are not moved, and loading the record logs a warning. When the location is on the SD card (or the declaration is `"sd"` and nothing has been chosen yet) and the card is absent, every call returns `unavailable`. `info()` returns both `location` and the declared `want`.
- The system never deletes a scene's files automatically: only the scene's own `remove`, the admin console, and deleting a scene with its data (`SceneRepository::remove(id, true)` plus `SceneFiles::remove_all()`) delete them. When a scene is deleted with its data while the card is absent, the `files/` on the card stays and a line is logged; when `scan()` or `on_sd_changed()` finds `scenes/<id>/files` on the card with no installed scene, it also only logs. Reinstalling with the same id reuses the files left behind: when there is no location record, the declaration allows SD, the card is present and the card already has `scenes/<id>/files`, the very first call (including read-only ones) adopts the card location and writes the record. When deleting with data fails on the device, `remove_all()` is called only if the scene is no longer installed (`scene.json` already deleted).
- `list()` returns at most `max_list` (256) names (the first 256 sorted by name); when truncated, `SceneFileList::truncated` is true and the Lua callback is `cb(err, list, truncated)`. The directory is walked entry by entry with `StorageManager::visit_dir`, keeping only the first 256, and looking up a single file also walks entry by entry, without collecting the whole directory in internal RAM (`count_dir` at startup still uses `list_dir`, because it deletes and renames as it walks). The SD card is FAT, where names are case-insensitive: when the card has no exactly matching name, matching is case-insensitive, and write, append, read, delete, download (including the in-progress duplicate-name check) and counting all act on the spelling already on the card; the reserved suffixes `.tmp`/`.new` are also refused case-insensitively.
- File names are `[A-Za-z0-9._-]`, 1–64 bytes, not starting with `.`, and may not end with `.tmp`/`.new` (the bookkeeping names of `StorageManager`'s own atomic writes). A single `write`/`append` is at most 256 KB and a `read` at most 64 KB (`too_large`). `write` goes through `write_atomic`, and `append` through `StorageManager::append()`.
- Usage is counted once at boot (`scan()`) and updated incrementally on every write after that; quotas are checked before writing. A download in progress reserves quota for the bytes received so far.
- Downloads use file-level two-stage naming: the response body is appended to `.<name>.dl` (which may be half-written and counts as garbage), and when complete it is renamed to `.<name>.done` (at this point it is always complete) → the old `<name>` is deleted → it is renamed to `<name>`. Counting a directory deletes any `.dl` that does not belong to a download in progress and completes every `.done` (when there is also a `<name>` file next to it, the `.done` is the newer one and `<name>` is deleted first; when `<name>` is a directory, neither is touched and only a log line is written, and finishing a download behaves the same). The HTTP client reports the status code through `HttpClientRequest::on_status` before the response body, and `SceneHttp` hands only 2xx response bodies to the download; a non-2xx body is read and discarded (up to the ordinary response limit, beyond which the transfer stops), uses no quota, and the callback gets `err=nil`, `size=0`, with the `.dl` deleted and the original file untouched. The download URL is checked against `http_hosts` on the scene task before the download starts (before the location is chosen), so a refused download never fixes a location.
- Threads: every method does file work and runs as a job of its scene (`SceneFiles::submit()`): on `wisp.sd.io` once the scene's files are known to be on the card, else on `wisp.fs`. A scene's calls stay on `wisp.fs` while one of its jobs routed there has not finished (an in-flight count per scene), so its jobs keep their order across the two workers. Each load of a scene's location record gets a new generation, and a card job carries the one it was routed with: a job that outlives a removal of the scene's files fails `Busy` instead of writing into files the scene has started again. After a card change, `sd_changed_begin()` (on `wisp.fs`) marks the card's scenes, `recount()` counts each one on `wisp.sd.io`, and `sd_changed_end()` (on `wisp.fs`) logs the files without a scene. A download stays on the worker it began on: its appends go there on the Bulk lane, and its finish goes through `FileDownload::submit()` behind them (on that worker's own thread it tries once, since nothing else could drain the lane meanwhile). The admin console's file routes (`routes_scene_files.cpp`) call them through `core::run_files()`, and the httpd thread only waits: a download reads one chunk at a time on the Bulk queue (at most 32 KB; the result is in the PSRAM buffer returned by `SceneFiles::read()`, held by a shared result slot), and the other calls go on the Normal queue; each wait is at most 5 s, and on timeout the request fails and the download ends early. `FileDownload::push()` runs on `wisp.shttp.dl`: it only copies the data into 32 KB PSRAM chunks and queues the append to the worker the download began on (`wisp.sd.io` or `wisp.fs`, Bulk lane), waiting when more than 128 KB is queued; `cancel()` (called by the runtime when a scene closes or fails, before `SceneHttp::cancel_scene`) wakes it, and afterwards `finish(false)` on that worker deletes the `.dl` (if it cannot be queued, the download is abandoned, `FileDownload::abandon()`, and the scene is counted again on its next call, which deletes it).

### `SceneStore` file format and logs

`core::SceneStore` (`components/wisp_core/include/wisp/core/scene_store.hpp`) is the persistence behind `wisp.store`: one key-value space plus at most 16 JSON record collections (spec 5.4/5.6; for the Lua-side API, see the "wisp.store" section of `docs/scene-api.md`).

- The index is all in memory, and reads and writes return immediately; persistence is asynchronous, as append-only logs: the key-value space writes `data/kv.log`, and each collection writes `data/<collection name>.log`. Each line is one JSON object, `{"op":"put","id":<id>,"v":<value>}` or `{"op":"del","id":<id>}` (the id in the key-value space is the key string itself; in a collection it is an integer), ending in `\n`. On load, a half line after the last `\n` is treated as a tail torn by power loss: it is discarded and the file is rewritten (`write_atomic`), because otherwise the next append would follow the torn bytes.
- The first pending write schedules a one-shot coalescing delay; when it expires, the pending content of each file is handed to `wisp.fs` together (`submit_io` on the device) to be written. When one flush involves several files, or a batch commit has more than one line, all the lines to be written are first written to `data/journal.json` (`write_atomic`), which is deleted once the flush is done; on reopening, any `journal.json` not yet deleted is replayed first (put/del are both idempotent), its lines appended, and then it is deleted. A failed flush is retried from 200 ms, doubling, up to 5 s.
- A log is compacted (rewritten with only the live records, still with `write_atomic`) when "dead bytes exceed half the live bytes" or "cumulative appends exceed a threshold". A compacted collection keeps one `{"op":"del"}` for the largest deleted id, so that id allocation stays monotonic after reopening.

### Development loop

- The simulator's `--scenes-dir` (see "Networking in the simulator" above): code is read straight from the local directory and the foreground scene reloads whenever a file changes, with no install/uninstall. This is the fastest iteration, but works only in the simulator.
- `tools/wisp_scene.py` (standard library only) is for the device or the simulator outside development mode, and pushes and manages scenes through the API of a paired admin console (connectivity spec 6.1, 6.3; scene spec 7.3):
  - `push <dir> [--open] [--watch]`: zips the directory with only `scene.json`, the entry file, `lib/**/*.lua` and `assets/**` and installs it on the device (`data/` is always skipped; that is the device's own storage); `--watch` compares a snapshot of the files every 0.5 s and pushes again automatically once changes have been quiet for 300 ms, and a scene running on the device reloads accordingly.
  - `ls`: lists installed scenes; `logs <id>`: subscribes to the admin console WebSocket's `log` and prints only lines tagged `scene.<id>`.
  - The first access to a device goes through pairing (the pairing code has to be read off the device screen and typed in); the token is stored in `<config dir>/scene_tool.json` (default `$XDG_CONFIG_HOME/wisp` or `~/.config/wisp`), with permissions 0600, written by atomic replacement. A 401 means the device has forgotten the token (revoked, or factory reset); pairing again fixes it.
  - The environment variable `WISP_SCENE_TIMEOUT_S` overrides the timeout of each request (default 30 s; the log-follow stream has no timeout and waits however long the device stays quiet).

## Agent, voice and shell (MVP)

Device layouts follow [the UI style guide](ui-style-guide.md): independent controls
have visible gaps, distinct groups have additional separation, and trailing icons
are vertically centred within their full rows. Shared Wisp spacing tokens apply
across all supported display shapes.

The data flow of a voice turn (mvp spec 1.5): talk key or a long press on the wisp → `wisp.voice` records and runs ASR → `ConversationController` hands the text to `AgentService::submit(…, Source::Voice)` → `wisp.agent` runs the LLM and tools → `SayParser` splits `<say>` out of the reply deltas → `VoiceService::speak()` does TTS sentence by sentence → `wisp.play` plays it. The screen (the home screen, or the talk overlay over any other screen) refreshes along with `TurnView`. Messages sent from the web page go through the same `AgentService`, only without being read aloud.

The wiring is in `App::start()`: `ReminderScheduler` loads the to-dos on `wisp.fs`; `AgentWiring` (`AgentService`, `MemoryStore`, tool registration, the admin console's `AgentApi`) and `VoiceWiring` (`VoiceService`, `PcmPlayer`, `ConversationController`, plus `TalkKey` when there is a talk key) are constructed before the shell, and once the shell is built it enters the home screen. Without `audio_in.main`, or without an `asr`/`tts` profile, voice degrades (`voice.state` reports the error reason, and Home lists the missing profiles), while the agent and web conversation work as usual.

### `wisp_agent` (agent core)

- Files: `components/wisp_agent/`: `agent_service` (queue, framing, confirmation, events), `turn_runner` (one turn: requests, compression, the length continuation, the rollover carry, tools), `calibration` (the estimate scale per profile and model), `conversation` (conversation log and archiving), `context` (context and compaction), `tool_registry`, `tools_*.cpp` (scene authoring and operation, UI, memory, to-dos, device, settings, docs, and `device.list`/`device.call` for self-describing devices in `tools_device_call.cpp`), `scene_workspace` (scene drafts and install checks), `docs` (the built-in docs of `docs.read`, generated by `tools/gen_agent_docs.py`). The App-side wiring is in `components/wisp_app/src/agent_wiring.{hpp,cpp}` (tool registration, the admin console's `AgentApi`, WS push).
- Task: `wisp.agent` (see the task table above, `flash_access = false`); tools that touch flash declare `ToolThread::Fs` (or `ToolThread::FsInteractive` for short writes someone waits for, on the Interactive lane) and run on `wisp.fs`, except the scene file tools, which run on `wisp.agent` and queue their file work as a job of the scene (`SceneFiles::submit()`).
- Limits: at most `agent`/`max_steps` tool calls and `agent`/`turn_min` minutes per turn (ranges and defaults: their rows in `kSettingsSchema`, `wisp/core/settings_schema.hpp`), set on the admin console's System page through `SystemSettings` (`agent_max_steps`, `agent_turn_min`). `AgentWiring` follows `SystemSettings::cell()` and calls `AgentService::set_turn_limits()`; each turn takes the limits at its start, so a change applies from the next turn on.
- Persistence: in the System area, `agent/current.jsonl` (the current conversation, `append()`ed entry by entry; it may begin with a `carry` line, the summary a rollover kept) and `agent/archive-<n>.jsonl` (archives), `memory/notes.json` (`core::MemoryStore`, at most 64 entries), `todo/todos.json` (`core::ReminderScheduler`, at most 200 entries); the last two are both written with `write_atomic`.
- Events: on the bus, `agent.state`, `memory.changed` and `todo.changed` (see the event topics above). In process there is also `AgentEvent` (`set_listener()`/`add_listener()`): `TurnBegin`, `TurnEnd`, `Delta`, `ToolPrep`, `ToolStart`, `ToolEnd`, `State`, `Confirm`, `Message`, `Cleared`. `TurnEnd` carries the turn's `status`, and for a turn that did not end `done` a `reason` (`stopped`, `step_limit`, `time_limit`, `no_model`, `unauthorized`, `network`, `network_lost`, `server`, `context`) and the `note` written to the conversation (at most `kSummaryChars` code points); `ConversationController` keeps them as `TurnView::end_reason`/`end_note` (4a spec 3.8). `ToolPrep` is emitted while the model is still writing a tool call: once as soon as the tool name arrives, and then, as the arguments grow, at most once every `net::LlmClient::kToolProgressMs`, carrying only the tool name and the number of argument bytes received so far, not the argument content; `ToolStart` is emitted only once the reply is complete.
- Context (4a spec 3.3, `wisp/agent/limits.hpp`): tool results of the running turn are sent whole up to `kLiveToolResultBytes` (96 KB), those of earlier turns are cut to `kToolResultKeepBytes` (4 KB); a call of an earlier turn whose arguments exceed `kCallArgsKeepBytes` is sent with the arguments `{"elided_bytes":N}`. `docs.read` returns a long topic in pages of at most `kDocsPageBytes`, with `total_bytes` and, while text remains, `next_offset` for the next call's `offset`. The bytes / 3 token estimate is scaled by a calibration per profile and model (`agent::Calibration`, 50-300 %, from the reply's `usage.prompt`, reset when the active profile or its model changes). Past `kCompressPercent` the oldest turns are summarized sparing `kKeepRecentTurns`, then sparing only the running turn; past the whole window the running turn's results are cut to `kToolResultKeepBytes`. A `context_length` refusal is retried once per turn after that recovery, unless it shrank nothing; otherwise the turn ends with reason `context`.
- Model requests go through `net::LlmProvider` (`wisp/net/llm_provider.hpp`: `active_model()`, `complete()`, errors as `net::LlmError`); `net::LlmClient` is its chat-completions implementation (4a spec 3.6): a 429, a 5xx and a transport failure that delivered no reply bytes share one budget of two retries (`kRetryDelaysMs`, 1 s and 4 s); a delta-seconds `Retry-After` replaces the delay, capped at `kMaxRetryAfterMs` and the call's remaining time, and gives up without retrying when the wait would reach the call's remaining time. A failure that came after part of the reply is not retried, so no text or speech is doubled. A failed response's body is read up to `kErrorBodyBytes` for `error.code`/`error.type`/`error.message` and discarded, never logged; only `LlmResult::code` (an identifier, dropped when any 8 or more bytes of it occur in the key or it holds the whole key) leaves the client. A bodiless 429 with a long `Retry-After` can run into the agent's 60 s stall check (`kStallMs`) and end the turn as `network_lost`. Dialect options of an `llm` profile (`out_tokens`, `out_field`, `reasoning`, `system_msgs`, `parallel_tools`) are resolved from the profile, then the preset's `defaults`, then the built-in value (llm-tool-providers spec 3.2), and shape the request body. A reply that ends with `finish_reason` `length` and no tool calls is continued once with a second request (spec 3.7); a second cut stores the text with a note.
- Confirmation: the agent deleting a scene (`scene.delete`) and deleting a scene file (`scene.files_remove`) are `ToolRisk::Confirm`, which opens a confirmation dialog on the device and runs only after the user taps "Allow"; adding, removing and changing memory notes and to-dos is `ToolRisk::Note`, with no confirmation, only a line of explanation left in the conversation. When the user deletes something themselves on the device or the web page, the UI still opens a confirmation dialog as usual, to prevent accidental taps.
- Logs (metadata only, never the user's or the model's text): `agent: turn <n> start source=<web|device_text|voice>`, `agent: state <s>`, `agent: tool <name> <ok|error:<code>> <ms> ms`, `agent: turn <n> end <status> steps=<k> tokens=<t>`, `agent: context <summarized|dropped> seq <a>-<b>`, `agent: carry <n> bytes` or `agent: carry skipped: <no_model|network|empty|cancelled|<llm error>>` (the summary a rollover carries into the new conversation), `models: profile <id>: dropped <n> invalid options` (a warning at load, naming only the profile and a count), and warnings when the context is still over the window or the model refused it as too long; each LLM request also logs a line `llm: model=<m> status=<s> ms=<t> tokens=<u>`, which for a failed request adds ` error=<error>` and, when the provider sent an error code that passed the key scrub (it is dropped when it holds the key or any 8 or more bytes of it), ` code=<code>`.

### Agent extension tools and headless scenes

The core tools include `http.fetch`, `lua.run`, `tools.find` and `tools.call`
(wire names replace dots with underscores). All four show an activity line
without device confirmation. API keys remain write-only. External content is
wrapped as untrusted data: `http:<host>` for fetch headers and body, `lua` for
Lua results/output/errors, and `scene:<id>` for scene tool descriptions/results.
The fixed security prompt treats such content as information, never instructions.

`net::SceneHttp` runs both Scene and Agent principals on two workers:
`wisp.shttp` for ordinary requests and `wisp.shttp.dl` for downloads, each
running its lane's requests one at a time in the order accepted (a download
and an ordinary request of one scene may complete in either order). Requests
are accepted only once both workers run. `TlsGate` is held only around connect
and handshake. Scene policy is unchanged. Agent identity `@agent` bypasses HTTPS-only,
host allowlist and rate policy, permits bounded redirect following, and fails
`offline` instead of entering the standby deferred queue. Syntax and resource
bounds still apply; cross-origin redirects drop credentials. Logs contain only
method, host, status and duration, never path, query, body or header values.

`scene::AgentRunner` creates a temporary budgeted VM on the existing scene task
for `lua.run`. Host-managed task coroutines wait for HTTP/files/sleep without
blocking other scene messages; CPU slices (200 ms, `kLuaRunSliceMs`) exclude
waiting, and the whole run still lasts its own `timeout_ms`. Agent files persist
under `<Library>/agent/files/`; factory reset removes them. No extra OS task is
created. Shared VM memory and large buffers use PSRAM.

`agent::ToolIndex` stores installed scene.json tool declarations in PSRAM and
refreshes after installation, rollback and deletion (including admin actions).
`tools.find` searches the index; `tools.call` validates parameters and dispatches
to `SceneRuntime::call_tool`. Scene tools never change the core model tools array
or fixed prompt, preserving the provider's prefix cache.

A stopped scene starts in `headless` state for a tool: tree without view or
`on_show`, with `on_state("headless")`, no background permission/count or boot
restore. It uses the shared VM budget and may evict background VMs when needed.
At most one headless scene exists, closing after 60 s idle after the last call;
opening it promotes the same VM without reload. Its launch reason stays `user`,
including later transitions. Overall call timeout cancels the task while keeping
a healthy scene; a VM CPU/memory fault uses normal scene fault handling.
Hardware RAM and prompt-injection acceptance remain user-run (agent-tools spec 8.2).

### `wisp_voice` (voice pipeline)

- Files: `components/wisp_voice/`: `voice_service` (the state machine of a voice turn, and wake locks), `capture_buffer`, `vad`, `asr_client` (`POST <base_url>/audio/transcriptions`, multipart), `tts_client` (`POST <base_url>/audio/speech`, `response_format: "pcm"`, a 16-bit mono PCM stream at the `sample_rate` of the `tts` profile, which is sent in the request only when the profile sets it, since OpenAI's request has no such field and strict servers refuse unknown ones), `say_parser`, `sentences` (sentence separators `。！？!?；;` and newlines; at most 200 code points read aloud per turn), `pcm_player`; constants are in `wisp/voice/limits.hpp`. The App-side wiring is in `components/wisp_app/src/voice_wiring.{hpp,cpp}`.
- Tasks: `wisp.voice` and `wisp.play` (task table), both declaring `flash_access = false`; the capture buffer and the TTS ring buffer are in `Mem::Large`.
- Recording has only one mode, push-to-talk (`CaptureMode::Hold`): no VAD runs; anything recorded for more than 300 ms (`kMinSpeechMs`) goes to ASR, and an empty recognition result shows "Didn't catch that" (`voice.state` goes back to `idle` with `result: "not_heard"`); at most 30 s. The `Vad` mode is still in `VoiceService`, but the shell does not use it.
- Priming (mvp spec 4.1): the press opens the mic (`prime()`) and keeps the last `VoiceConfig::preroll_ms` (`kPrerollMs`, 500 ms; 0 turns priming off) as the head of a hold's recording, where the start tone is recorded too; a press that does not become a hold closes it (`unprime()`), and so does `kPrimeMaxMs` (2 s). No priming while the output plays, during a capture (such a press is spent with it), or for a talk-key press made with the screen off; those holds take the unprimed path. `kMinSpeechMs` counts the hold after the pre-roll; `max_record_ms` caps the two together. The capture log gains `preroll_ms=`.
- Offline at a hold's start with a network expected (`VoiceDeps::network_expected`, from `WifiService::connection_expected()`: Wi-Fi enabled by the user, retries not held by a user disconnect, a saved network not parked for a rejected password, and the state connecting or connected, or the radio off only for deep standby, e.g. reconnecting after deep standby; a backoff, such as a saved network out of range, does not count), the hold records, and recognition waits up to `kNetWaitMs` (8 s) while the network stays expected; offline and not expected is the `offline` error at once.
- A voice turn holds three wake locks of `system.voice`, `screen`, `network` and `cpu`, from the start of recording until the speech has finished playing (or an error, a cancel or an interruption), and only then releases them. At most two model connections exist at the same time (the LLM stream plus one TTS request, `wisp/net/tls_gate.hpp`): while the LLM streams, only the first sentence is synthesized, and the later ones only once the reply's `<say>` block has closed (`SayParser::Out::say_end` → `VoiceService::say_closed()`); the sentences still go one TTS request at a time (mvp spec 4.5).
- Events: `voice.state` (event topics). Logs: `voice: state <s>`, `voice: capture ms=… preroll_ms=… speech_ms=…` (only durations and level statistics), `voice: tts n=<sentence number> chars=<code points> ms=<duration> status=<HTTP status>`; neither the recognised text nor the spoken text is logged.
- Settings: `voice`/`tts_mute` (boolean; default in `kSettingsSchema`) mutes spoken replies; the text is still shown on the screen.

### `wisp_shell` (system shell)

- Files: `components/wisp_shell/`: `shell` (pages and drag navigation), `home` (home screen), `history` (conversation history page), `scene_list` (scene list page), `settings_page` (Settings page), `choice_page` (its choice pages), `page_frame` (the sub-pages' frame and rows), `talk_overlay` (the talk overlay over any screen but Home), `conversation` (`ConversationController`), `talk_key` (talk key), `activity` (step labels), `gestures`, `mood` (wisp expressions), `scene_recents` (the order of the scene list, `shell/recents.json` in the System area); constants are in `wisp/shell/limits.hpp`. The wisp itself is `ui::WispView` in `wisp_ui`.
- The device boots into the home screen: the wisp on a black background (white on e-paper). At rest it takes 55% of the safe area's short side (`kWispIdlePercent`), with its centre at 42% of the safe area's height (`kWispIdleCentrePercent`). During a turn it shrinks to 28% and moves up, with what it heard above it and the scrolling reply below it (the `<say>` part in large type). While a turn is in progress and there is no reply text yet, the reply area lists the agent's steps (the last 4, one line each, appearing on `ToolPrep`/`ToolStart` and ticked or crossed on `ToolEnd`) and "Step N · elapsed time" (第 N 步 · 用时); once there is text, only one line "Steps: N · elapsed time" (用了 N 步 · 用时) remains.
- Talking: the talk key (the button whose caps have `role: "talk"`, `button.vol_down` on both the reference board and the simulator, which is the BOOT key on the device) starts after being held for 300 ms and sends on release; a long press on the wisp on the home screen does the same. A single tap on the wisp does not trigger voice (it is reserved for future character interaction). While holding the talk key, swiping up on the screen cancels this recording. A press primes the mic (`ConversationController::press_begin()`) and every press that does not become a hold releases it (`press_end()`). With the screen off, the talk key's press wakes the screen and, held 300 ms, starts an unprimed capture (an EdgeEvent key only: a PollOnly key is not read in standby). A tap on the wisp shows "Hold the wisp to talk" (`HomeHoldToTalk`) once everything is set up. A hold stops the speech and records but leaves a running turn (a scene build from the web page, say) running; the hold's transcript stops the running or waiting turn just before it is submitted, and a cancelled hold or one that heard nothing stops nothing (mvp spec 4.4).
- Readiness (`shell::Readiness`, mvp spec 6.6): `net` (Up, Connecting while a connection is expected (`network_expected`), Down), `llm`, `asr`, `tts` (muted counts as set). A hold needs `can_talk()` (not Down, llm and asr), so it records while Wi-Fi reconnects; Home's hint lists what `complete()` lacks: no Wi-Fi, connecting, no models at all, or "Needed:" items (`HomeMissing` with `HomeNeed*`), with the admin address; while `can_talk()` holds, a fresh voice error, "not heard" or turn outcome shows instead of the items for its `kFadeAfterMs`.
- Stopping a turn: while any turn runs the home screen shows a Stop button (`HomeStop`) right of the wisp, a 48 px target (`kStopPx`), which calls `ConversationController::stop_turn()`. When a turn ends other than `done`, the home hint shows a short per-reason string (`HomeTurn*`), with the admin address after `no_model`/`unauthorized` in the idle layout, until the next turn or capture (mvp spec 6.2).
- Navigation follows the finger (mvp spec 6.3): on the home screen, drag right into Settings, left into the scene list, and down into the conversation history, and drag the opposite way back to the home screen; swiping down from the top edge is the system layer's pull-down panel. After dragging 2% of the screen's shorter side (10 px on a 480 px screen, the same as the LVGL scroll limit that `UiRuntime` sets), both pages follow the finger together; on release, the move completes if it went past 1/3 or was flung fast enough, and otherwise springs back. Every page change logs a line `shell: page <home|settings|scenes|history>`. The scene list appears as soon as it opens, with the last listing when it is still current; otherwise the task `wisp.shell.list` reads it (one storage job per scene) and decodes the icons, and the cards come first, the icons as they decode.
- Hardware diagnostics (the former self-check screen) is no longer the first page: Settings → System → Hardware diagnostics, or the serial command `diag`.
- Settings page (mvp spec 6.4): a grouped list; a value row (screen off, deep standby, language, time zone, time format) opens a choice page (`choice_page`) over it, built by `Shell::open_choice()`. Its rows, ranges, choices and labels come from the settings schema (`wisp/core/settings_schema.hpp`), and while it is open it follows the settings cell on the UI thread, so a change made by voice or on the web page shows at once; a row keeps the value just picked while its own write is in flight and goes back to the stored value when that write did not store. A tap on a choice writes the setting and slides back to Settings; a right drag goes back without writing, following the finger like the other pages. The shell logs `shell: choice open` and `shell: choice closed`. A language change (`ui::lang()`, set by the system duties from the settings cell) is noticed by the shell's 250 ms timer: it closes any choice page, re-texts the home screen and rebuilds the open sub-page in place, keeping its scroll position, and logs `shell: language <code>`. Its Restart and Power off rows ask first in the system layer's confirm dialog; Yes posts `ShellDeps::restart` (App: `flush_storage()`, then `Platform::reboot`) or `ShellDeps::power_off` (App: `SystemDuties::power_off()`, the same path as a confirmed power-key long press), and a row is left out when the platform cannot do it.
- Talking with any screen but Home in front (a scene, a sub-page, a choice or Wi-Fi page, the diagnostics): a talk overlay (`TalkOverlay`) is laid over the screen, showing the recording level, the step being executed and the `<say>` text of a voice turn, and the same short turn-end or voice-error string Home shows (Note phase), without touching the screen's own UI; a turn from the web page or device text shows nothing while it runs, only its Note if it fails. The card grows to at most three lines, then ends with an ellipsis. While the card shows, the sub-pages (`page_frame`, through `set_overlay_end_room()`) and the diagnostics (through `ShellDeps::diagnostics_end_room`) end their scroll range kGapSm above the card at its current height (`TalkOverlay::end_room()`), so their last item can be scrolled clear of it; once it hides they scroll exactly as without it. Tapping it returns to the home screen; Home coming in front hides it, and a change of the scene runtime's overview cell (`SceneRuntime::overview()`) only has it re-evaluate (mvp spec 6.5). The shell follows the voice state through `ConversationController::voice_status()` (subscribed on the UI thread from `Shell::start()` or `Shell::set_conversation()`) and reads the recording level from `voice_level()` when it draws: while the card shows Listening with the screen on, its timer runs every 50 ms and moves the level bar alone, otherwise every 250 ms. An open scene list lists again (on `wisp.fs`) when the overview's catalog counter, foreground scene or background count moves; a headless scene alone lists nothing.
- Settings: `sys`/`time_24h` (boolean; default in `kSettingsSchema`) picks a 24-hour or a 12-hour clock for every wall-clock time the device shows (`ui::format_clock()`, `wisp/ui/clock_text.hpp`); scenes read it as `wisp.device.info().time_24h`.
- Threads: the pages are all on the UI thread; the callbacks of `ConversationController` come from `wisp.agent`, `wisp.voice` and the event bus, and only record the change and post one refresh (`UiRuntime::post()`).

## Refinements relative to the spec (verified before implementation, confirmed by the user)

1. Two new portable components: `wisp_base` (`Result`, `ErrorCode`, `Value`/`Properties`, JSON conversion, below os/hal) and `wisp_app` (boot orchestration + the self-check screen, above ui). The spec's `wisp_ui` keeps only the LVGL runtime.
2. The touch chip is actually the **CST9217** (both the MyOS code and Waveshare's official BSP say so; the CST9220 in the MyOS hardware document is wrong), and the driver is `waveshare/esp_lcd_touch_cst9217`.
3. The SD card follows Waveshare's official BSP and uses **1-bit SDMMC** (CLK=GPIO2, CMD=GPIO1, D0=GPIO3), not the SPI the spec says.
4. The display, touch, audio codec and SD card are initialised as esp_board_manager devices (the YAML follows the verified definition of the same board in ESP-Claw, Apache-2.0, with the source credited); the IMU, PMU, RTC, buttons and the internal LittleFS are initialised by Wisp's own drivers, on the I2C bus bmgr provides.
5. `hal::Button` provides level reads and optional timestamped EdgeEvent input; the portable `ButtonService` decides short and long presses uniformly (long-press threshold 1000 ms), with per-device standby polling policy (see "Button input and standby").
6. Pinned versions: ESP-IDF **v6.0.3**, LVGL **9.5.0**.
7. Fonts: body text (16 px and below) is a bitmap font: `lv_font_montserrat_16` (Latin and the `LV_SYMBOL_*` icons) falls back to `lv_font_wisp_icons_16` (the Wisp icons LVGL's set lacks, `WISP_SYMBOL_*` in `wisp/ui/symbols.hpp`, generated by `tools/gen_icon_font.py`) and then to `lv_font_cjk_16` (16 px, 4bpp; GB2312 ∪ Japanese kana and symbols ∪ JIS X 0208 level-1 kanji, generated by `tools/gen_cjk_font.py` from upstream Noto Sans CJK SC, see connectivity spec 8.3 and `docs/references.md`). What `UiRuntime::default_font()` returns is these fonts wrapped in an 8-bit glyph cache (`components/wisp_ui/src/a8_font.cpp`, `Mem::Large`, capped at 512 KB): a glyph is expanded the first time it is drawn, and after that takes LVGL's static A8 bitmap path, drawing pixel-for-pixel the same as the original font. From 20 px up it is a vector font: `ui::font(px)` takes the largest step no bigger than the requested pixel size (20, 24, 28, 32, 40, 48, 64, 80, 96, 128) and renders the Noto Sans CJK SC vector subset from the `fonts` partition image through LVGL's Tiny TTF (stb_truetype), with the glyph cache in PSRAM. The fallback chain is vector font → icon font (`lv_font_wisp_icons_{24,32,48}`, which also hold the Wisp icons, the 48 px one only 15 common icons and falling back to the 32 px one; the largest size no bigger than the step; none for the 20 step) → body font, and the `LV_SYMBOL_*` and Wisp icons the vector font lacks, as well as characters outside the character set, all land on this chain (vector font spec 4.1, 4.2). When the font image is missing or corrupt, or creating a step fails, it only degrades to "icon font → body font"; `UiRuntime::start()` still succeeds and boot is not blocked (vector font spec 3.6). The line height and baseline of the vector steps are rewritten as `line_height = ceil(0.28·px) + ceil(0.99·px)` and `base_line = ceil(0.28·px) − 1` (rather than the noticeably taller line height Tiny TTF computes from `hhea`), so that the glyphs with the highest and lowest ink in the character set both fall inside the line box that clips to the label's text area (vector font spec 4.3).
8. Simulator screenshots use a built-in minimal PNG encoder (uncompressed deflate), with no third-party image library.
9. New performance monitoring (not required by the spec): `UiRuntime` itself measures FPS, UI thread utilisation and average flush time; hardware diagnostics shows them, and the system duties print a line `WISP_PERF <json>` every 5 s; LVGL's bundled sysmon overlay can optionally be turned on. This serves as the performance regression baseline for the later scene runtime. Opaque cards laid over content are registered with `ui::mark_opaque_overlay()` (`wisp/ui/overlay.hpp`); currently these are the Wi-Fi setup card and the pairing card on `lv_layer_top()` (`make_card()` in `net_cards.cpp`; the confirmation dialogs are `lv_msgbox` and are not registered). When the content below scrolls, only the part outside the card is redrawn, while changes to the card itself are redrawn as usual. When the card or any of its ancestors is hidden or stops being fully opaque (opacity, blend mode, mask, transform), or the invalidated area touches another object on the top or system layer, it falls back to redrawing the whole area; the first refresh after the card stops covering redraws the whole of its area from the previous frame; no clipping is done while LVGL is rendering. Rendering acceleration is chosen per chip; see `docs/porting-guide.md`.
10. Screen shape and safe area (added during implementation with the user's approval, spec section 5.6): the Display caps `shape` takes `rect`/`rounded_rect`/`circle` (the former `rounded_square` was renamed to `rounded_rect`); `wisp_hal` provides the geometry functions `visible`/`safe_rect`/`row_span`; the capability list attaches `safe_area` to the Display entry; and both the self-check screen and the simulator mask follow it.
11. Screen-off power saving (added during implementation with the user's approval, spec section 6.7, acceptance item 5): a new `PowerManager` puts the device into standby when the screen turns off, at which point the display and touch go to sleep, the UI stops rendering and button polling slows down; on the device, DFS and automatic light sleep in standby are enabled; idle automatic screen-off is also supported. Background scenes and wake locks were left to sub-project 3 (spec 1.6).
12. The scene runtime added two rules for opaque overlays and the back gesture (ruled during implementation, scene spec 3.5):
    - The `wisp::ui::overlay` marking gained `OwnChanges::InOwnEvents`: for overlays whose content may cover the whole screen but changes only within the events they receive themselves, currently the on-screen keyboard and the pinyin candidate row (`build_keyboard()` in `system_layer.cpp`). While they handle their own events, invalidated areas inside them are still treated as covered; at any other time, any invalidated area that touches them falls back to redrawing the whole area as before. The error panel is marked with the original default rule (`OwnChanges::InsideBox`); the confirmation dialog (the `lv_msgbox` built by `SystemLayer::open_confirm()`, with LVGL's own full-screen backdrop) is not marked and gets no skipping: while it is open, the invalidated area of the backdrop itself touches it, so it naturally falls back to redrawing the whole area, with no extra rule needed. Every time `SystemDuties::raise_overlays()` resyncs the overlays (language switch, Wi-Fi/pairing state change), it first `raise()`s the Wi-Fi setup/pairing cards, then `raise()`s `SystemLayer` (error panel, keyboard, candidate row, back arrow, confirmation dialog), so that they always stay above the cards.
    - The back gesture creates no resident object: `SystemLayer::hook_pointer()` wraps the input device's read callback and passively listens to every read (without swallowing events). It takes over only a touch that starts within 8% of the screen's shorter side of the visually visible left edge and moves right by 5% of it, at any angle (38 px and 24 px on a 480 px screen; every edge-gesture distance is a share of the shorter side, `hal::share_of_screen()`) (consistent with Android's edge back gesture: however far it moves up or down does not matter, only the distance to the right). Before it takes over, the touch reaches the scene normally; dragging the finger back within the trigger distance before releasing cancels it without going back. Once the swipe passes 2% of the shorter side (`kBackArrowSlopPercent`, so the arrow does not flash when scrolling along the edge), an unmarked back arrow that follows the finger appears at the left edge, and the frame after it is hidden redraws the whole area it covered as usual.
13. Device theme (added during implementation with the user's approval): `wisp/ui/theme.hpp` is the single source of colours, corner radii and spacing on the device. Its values come from the web console's dark tokens (`web/styles/tokens.css`); the console's translucent tokens (borders, soft background tints of status colours) are pre-blended onto `surface` here and become opaque colours. The device has only the dark set: a dark background suits self-emissive screens and is also the brand's base tone. The colour tokens are in `wisp/ui/theme_tokens.hpp`, which does not depend on LVGL, and `theme.hpp` adds the parts that depend on LVGL. `UiRuntime::start()` layers a Wisp theme over LVGL's default (dark) theme, so native widgets get this look without styling each one; buttons are coloured by `ui::ButtonRole` (Primary/Secondary/Danger): the confirm button of a dialog is Primary, confirmations that destroy data (factory reset, deleting a scene) are Danger, and cancel is Secondary. The scenes' colour tokens (scene runtime spec 4.4) keep their names, with values mapped onto the same set of colours.

### Device connection shortcuts

`wisp::shell::ConnectionsPage` provides Wi-Fi control and existing model profile shortcuts from Settings. It uses `WifiService` and `ModelProfileService`, with blocking scans, connection requests and probes submitted to NetWiring's bounded `wisp.netcfg` worker (four pending operations). UI results return through `UiRuntime::post()` and are discarded after the page closes. Model creation, editing and deletion remain in the web console. The worker uses a normal PSRAM-eligible stack; persistent writes still go through `StorageWorker`.

`net/wifi.json` stores an optional `enabled` boolean, defaulting to true for existing files. User disable shuts down STA and the setup hotspot without deleting credentials, and takes precedence over power transitions and network windows. On supported power devices, `wisp.net` reconciles `usb_present` of `PowerMonitor::last_status()` (on every loop, and woken promptly by `PowerMonitor::supply()`; it reads the status rather than the cell because the cell keeps the last good sample through a failed read) and holds `system.powered_wifi` (network) while external power and user Wi-Fi enable are both present, including a full battery. This permits screen-off standby while keeping Wi-Fi; unplugging, unknown power or user disable releases only that lock.

`WifiService::disconnect()` keeps the radio and saved credentials, cancels the current connection and retries, and suspends automatic reconnection across power transitions. An explicit connection, a user Wi-Fi off/on cycle or reboot resumes it. The settings page removes both the current-network shortcut and nearby rows immediately when the switch is turned off. The status panel reads the cached `wifi_enabled` flag separately from link state: disabled Wi-Fi has no indicator; enabled but disconnected Wi-Fi retains its status. Network events refresh an open panel.


Automatic light sleep is allowed by default and can be disabled at build time with `WISP_ENABLE_LIGHT_SLEEP=OFF`. System settings no longer expose `light_sleep`; `/system/power` retains the actual state for diagnostics.
